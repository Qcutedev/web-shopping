## Actors and trust boundaries

Anonymous visitor, customer, seller (pending, approved, suspended), admin, and an external attacker who may hold any non-admin account. Trust boundaries: browser to server (everything from the browser is untrusted, including every request header), reverse proxy to server (trusted only as configured in SR-01), server to database, server to file storage, server to log collector, and later server to payment and shipping providers (inbound webhooks are untrusted until signature-verified).

## Security rules decided by the security owner

These are binding on the code named in each rule. They are technical rules; none of them decides a product or business matter.

### SR-01 Trusted proxy and client address (decided 2026-10-11)

Resolves the "per IP" half of review item S20.

**Rule.** The client address used for rate limiting and security logging comes from exactly one function, `getClientAddress(request, config)` in `src/server/client-address.ts` (backend-api), where `config` is `{ trustedProxyHops, trustedClientIpHeader? }`. The function does not read the environment: the caller passes the validated configuration in, and the exported constant `NO_TRUSTED_PROXY` is the default. No other code reads `X-Forwarded-For`, `Forwarded`, `X-Real-IP`, or any similar header. What the function trusts is set only by environment variables validated in `src/server/env.ts` (devops):

| Variable | Values | Default | Meaning |
| --- | --- | --- | --- |
| `TRUSTED_PROXY_HOPS` | integer 0 to 5 | `0` | Number of reverse proxies between the internet and the application that the operator controls and that each append the address they received the connection from to `X-Forwarded-For` |
| `TRUSTED_CLIENT_IP_HEADER` | header name matching `^[A-Za-z0-9-]{1,64}$`, or unset | unset | Name of a single-value header that the hosting platform's proxy always overwrites with the client address (for platforms that document one). Not `X-Forwarded-For`, `Forwarded`, `Cookie`, `Authorization`, or `Host` |

Derivation:

1. `TRUSTED_PROXY_HOPS=0` and no `TRUSTED_CLIENT_IP_HEADER` (the default): no request header is read. The client address is **unknown**.
2. `TRUSTED_PROXY_HOPS=n` with n of 1 or more: split the combined `X-Forwarded-For` value on commas, trim each entry, and take the entry n places from the right end (n = 1 is the last entry). Entries to the left of it are client-controlled and are never used. Fewer than n entries means unknown.
3. `TRUSTED_CLIENT_IP_HEADER` set: use that header's whole value. Missing, or containing a comma, means unknown.
4. The candidate must parse as an IPv4 or IPv6 address (`node:net` `isIP`), after removing an IPv4-mapped prefix (`::ffff:`). Anything else is unknown. No brackets, ports, zone ids, or host names are accepted.
5. Normalise: IPv4 as dotted decimal. IPv6 is reduced to its /64 network (first four groups of the fully expanded, lower-case form), because one subscriber normally controls a whole /64 and could otherwise rotate through 2^64 addresses.
6. Unknown addresses share one rate-limit subject, the literal `unknown`. They are never given a fresh or random subject and are never exempt from a limit.

Decisions on the implementation (security owner, 2026-10-11, after reviewing `src/server/client-address.ts`):

- **Text form of an IPv6 network: accepted.** The result is written as the four expanded groups followed by `::/64`, for example `2001:0db8:85a3:0000::/64`. It is an opaque subject and a log value; nothing may parse it back into an address. Every spelling of an address in one /64 gives the same string (tested).
- **Hexadecimal IPv4-mapped form (`::ffff:cb00:7107`) resolves to `unknown`: accepted.** Only the dotted form (`::ffff:203.0.113.7`, any letter case) is converted to the IPv4 address. Fully written-out forms (`0:0:0:0:0:ffff:...`), `::`, and `::1` fall into the all-zero network `0000:0000:0000:0000::/64`. All of these are shared subjects, so the failure direction is a shared allowance, never a fresh one, and a client cannot choose the spelling because the entry is written by the trusted proxy. The staging check in "Deployment conditions" must confirm that the proxy writes plain IPv4 or the dotted mapped form.
- **An invalid configuration throws `TypeError` on every call: accepted.** A configuration outside the table above must never widen what is trusted, and an exception is the fail-closed result. Two conditions: `src/server/env.ts` rejects the same values at startup so that the throw is never reached in a running deployment, and handlers call `getClientAddress` inside the `try` block that ends in `errorResponse`, so that a throw becomes a 500 and not an unhandled rejection.
- **Ports are not accepted.** A proxy that appends `address:port` (some cloud load balancers do) makes every client `unknown`. That is the safe direction, and it is another thing the staging check must catch.

`src/server/env.ts` must:

- reject a value outside the ranges above, and reject both variables being set at once (`TRUSTED_PROXY_HOPS` greater than 0 together with `TRUSTED_CLIENT_IP_HEADER`);
- when `NODE_ENV=production`, require that `TRUSTED_PROXY_HOPS` is set explicitly (no silent default) and, if the result is "no proxy trusted", log one warning at startup that every per-address limit is shared by all clients;
- never accept a boolean "trust proxy" switch.

**Reason.** Measured in the installed framework: Next.js 16.4.0 does not give a route handler the TCP peer address. `node_modules/next/dist/server/base-server.js:567` runs `req.headers['x-forwarded-for'] ??= socket.remoteAddress`, so when a client sends its own `X-Forwarded-For` the framework keeps the client's value and the real address is lost. With no proxy, the header is therefore exactly as trustworthy as any other client input: not at all. An attacker who can choose the address gets unlimited sign-in attempts (a new "address" per request), can spend another network's allowance to lock it out, and can fill the limiter store (SEC-004). Counting hops from the right is the only position a client cannot influence, because each trusted proxy appends what it saw itself. The deployment target is not chosen, so the rule supports both the append style and the single-header style without guessing which platform will be used.

**Consequences that are intended.** With the default configuration every anonymous client shares one bucket, so sign-in is limited to 5 per minute for the whole site. That is safe and unusable, which forces the proxy to be configured before any real deployment rather than leaving limits silently bypassable. Local development and tests are unaffected in practice.

**Deployment conditions (devops, `docs/DEPLOYMENT.md`).** When either variable is set, the application port must be reachable only from the proxy (loopback or a private network); otherwise a client can connect directly and forge the trusted position. The proxy must append to or overwrite `X-Forwarded-For` (never pass a client value through as the last entry) and must overwrite the header named in `TRUSTED_CLIENT_IP_HEADER`. The hop count must be confirmed on staging by a request from a known address before production.

**What other code must do.**

- auth (T-015): the auth library's own address detection and built-in rate limiter must not read `X-Forwarded-For` by themselves. Either feed them the SR-01 result or switch them off and use `src/server/rate-limit.ts`. To be validated against the installed library version (review item V10).
- backend-api: rate-limit subjects are built only from `getClientAddress`, `actor.userId`, or a normalised email (trimmed, lower-cased, Unicode NFKC). A per-email subject is consumed only after the per-address check has allowed the request, so one address cannot create unlimited per-email keys.
- Nobody uses the client address for authorization, and nobody stores it outside security log lines (SR-04, kept as SR-06 says) and the session record (SR-07).

### SR-02 Rate limiter at the key cap (decided 2026-10-11)

**Rule.** Keep fail-closed: when a store is full of live windows, a subject that has no window yet is refused with 429. Live counters are never evicted and the limiter never fails open. This is conditional on four changes, tracked as SEC-004 and SEC-005:

1. **Isolated capacity per rule.** Each rule (sign-in by address, sign-in by email, sign-up, checkout, uploads, seller application, review create) has its own key capacity, so filling one cannot refuse another. The sum of all capacities stays bounded and documented in the module (at most 200,000 windows in total).
2. **The rule is part of the key.** The limiter API takes the rule's name and builds the stored key itself (`<rule>:<subject>`); a caller cannot make two rules share a counter or a window.
3. **Short retry at saturation.** A refusal caused by a full store reports a `Retry-After` of at most 60 seconds, not the rule's whole window (today it is up to 24 hours).
4. **Visible.** Saturation writes one `warn` line per rule per minute at most (rule name and store size only, never the keys) and is distinguishable from an ordinary limit hit in the result, so operators can alert on it.

**Reason.** The alternatives are worse. Failing open means anyone who can fill the store switches off brute-force protection for every new subject, which is the exact moment an attacker wants it off (TM-01). Evicting the oldest or a random live counter lets an attacker reset their own or a victim's counter by flooding. Failing closed costs availability only, and only for subjects that have no window yet. The cost is real: verified on 2026-10-11, 100,000 distinct sign-up keys (one-hour windows) make the shared store refuse every new checkout, upload, and sign-in key for up to an hour. Isolation limits that damage to the rule being flooded; per-user rules can then only be filled by as many signed-in accounts as their capacity, and anonymous rules are bounded by SR-01 (one key per IPv4 address or IPv6 /64, per-email keys only after the address check).

**Accepted remainder.** An attacker with tens of thousands of distinct networks can still make sign-up or sign-in refuse new subjects while the flood lasts. That is a volumetric attack which an in-process limiter cannot solve; see residual risks.

**Capacity split (decided 2026-10-11): accepted as implemented.** `sign-in-address`, `sign-in-email`, and `sign-up` hold 40,000 windows each; `checkout`, `uploads`, `seller-application`, and `review-create` hold 20,000 each; the total is exactly 200,000. The anonymous rules get the larger share because their subjects are the cheapest to vary. What the numbers mean in practice:

- A signed-in rule can only be filled by 20,000 distinct accounts acting inside one window, and account creation is itself limited by `sign-up`.
- `sign-up` (one-hour windows) is filled by 40,000 distinct addresses or IPv6 /64 networks inside an hour. **One IPv6 /48 contains 65,536 /64 networks**, and a /48 is what many hosting providers and tunnel brokers hand to a single customer, so one such customer can keep `sign-up` refusing new networks with about 11 requests a second. The same holder needs about 670 requests a second to do it to `sign-in-address` (one-minute windows). Existing subjects keep their counters and nothing fails open; the cost is that new visitors cannot sign up or sign in while the flood lasts. This is part of the accepted remainder above and is listed in residual risks; an aggregate limit per /48 or upstream rate limiting is the answer if it is ever observed, and the saturation warning is how it would be observed.
- Because the total is used up, a rule added later does not fit. Today that makes whichever rule is used last throw at run time (SEC-018). Any new rule must come with a new split recorded here.

**Custom stores.** `MemoryRateLimitStore` accepts a smaller total (`maxKeys`) for tests; with a total below the sum of the rule capacities the rules compete again and are not isolated. Production code must use the default.

### SR-03 Client-supplied request ids (decided 2026-10-11)

**Rule.** By default the server generates every request id (`crypto.randomUUID()`) and ignores an incoming `X-Request-Id`. An incoming value is reused only when both hold: the deployment has a trusted proxy configured under SR-01 (`TRUSTED_PROXY_HOPS` of 1 or more, or `TRUSTED_CLIENT_IP_HEADER` set), and the value matches `^[A-Za-z0-9_-]{8,64}$`. The proxy is then expected to set or overwrite the header. `resolveRequestId` must take the trust decision as an explicit argument that defaults to "do not trust"; it must not read the environment by itself. When an untrusted client sends a well-formed id it may be logged as a separate field named `clientRequestId`, never as `requestId`.

**Reason.** The request id is how one request is found in the logs and what a user quotes from an error message. If any client can choose it, an attacker can reuse the id of someone else's request (ids are shown in error bodies and response headers) or one id for thousands of requests, which makes the log trail of an incident ambiguous exactly when it is needed. The format check already prevents header and log injection (verified), so the remaining harm is to log integrity only, hence Low (SEC-003). A proxy that sits in front of every request is a legitimate source of ids because it lets proxy logs and application logs be joined.

### SR-04 Data that must never appear in logs (decided 2026-10-11)

Review of `docs/DATA_MODEL.md` (draft schema v1). Logs identify people and things by opaque id only: `userId`, `storeId`, `orderId`, `orderNumber`, `sellerOrderId`, `productId`, `addressId`, `requestId`.

**Never logged, at any level, including inside error objects:**

| Class | Fields (data-model names and the request fields that carry them) |
| --- | --- |
| Credentials and secrets | passwords and password hashes (`Account.password`), session tokens and session ids, cookies, `Authorization` values, `Verification.value`, any provider access, refresh, or id token, API keys, `AUTH_SECRET`, connection strings with credentials, `ADMIN_BOOTSTRAP_PASSWORD`, one-time codes |
| Email | `User.email`, `ADMIN_BOOTSTRAP_EMAIL`, an email typed into a sign-in or sign-up form |
| Phone | `User.phone`, `Address.phone`, `Store.contactPhone`, `SellerApplication.contactPhone`, `Order.shipPhone` |
| Personal name | `User.name`, `Address.recipientName`, `Order.shipRecipientName` |
| Address, every part | `Address.line1`, `subdistrict`, `district`, `province`, `postalCode`, and the `Order.ship*` copies. Province and district are included: with an order time they narrow down a person, and one rule for the whole address is harder to get wrong |
| Free text written by users or about users | `Review.comment`, `SellerApplication.description`, `SellerApplication.reviewNote`, `Store.statusReason`, `Product.moderationNote`, `Payment.failureReason`, `AuditLog.metadata`, catalog search text (`q`) |
| Parcel identifiers | `Shipment.trackingNumber` (it leads to a recipient's name and address at the carrier) |
| Whole payloads | request bodies, query strings, header collections, database rows, and Prisma arguments, in any form |

**Allowed with limits:**

- The client address from SR-01 may be written under the single key `clientIp`, and only on security events: a rate-limit refusal, a failed or successful sign-in, a sign-up, an `Origin` check failure, and an admin action. It is personal data; those lines are kept 90 days and may be read by system administrators only (SR-06, owner decision of 2026-10-11). Any other address-like key (`ip`, `ipAddress`, `remoteAddress`, `x-forwarded-for`, `x-real-ip`, `forwarded`) is redacted.
- `User-Agent` may be logged on the same security events, truncated to 200 characters.
- Store names, product titles, SKUs, and category names are public catalog data and are not personal, but ids are still preferred.

**What the logger must do (backend-api, `src/server/logger.ts`; SEC-001, SEC-002, SEC-007, and the additions of 2026-10-11 tracked as SEC-012 to SEC-016).** Key matching stays case-insensitive on the key with non-alphanumeric characters removed.

- Redact when the key **contains**: `password`, `passwd`, `pwd`, `passphrase`, `token`, `secret`, `authorization`, `cookie`, `session`, `apikey`, `credential`, `privatekey`, `signature`, `jwt`, `email`, `phone`, `recipient`, `postalcode`, `district` (also covers `subdistrict`), `province`, `street`, `forwarded`.
- Redact when the key **equals**: `sid`, `pass`, `pin`, `otp`, `hash`, `name`, `fullname`, `firstname`, `lastname`, `displayname`, `address`, `shippingaddress`, `billingaddress`, `addressline1`, `addressline2`, `line1`, `line2`, `shipline1`, `ip`, `ipaddress`, `remoteaddress`, `clientaddress`, `realip`, `xrealip`, `comment`, `description`, `reviewnote`, `statusreason`, `moderationnote`, `failurereason`, `metadata`, `trackingnumber`, `q`, `query`, `body`, `headers`, `rawheaders`. `address` is matched exactly, not as a substring, so that `addressId` stays readable.
- The exact key `name` is redacted on ordinary objects but an `Error`'s own `name` (for example `AppError`, which sets it as an own property) must still be written. Use `module` or `component`, not `name`, for logger bindings.
- In every string, wherever it appears (messages, error messages, stacks, values under harmless keys): mask URL user-info up to the **last** `@` before the host (a password containing `@` currently leaks its tail), mask the values of URL query parameters whose names match the "contains" list, mask `key=value` and `key: value` pairs whose key matches the "contains" list (covers `password=...` and a raw `Cookie:` header line), mask `Bearer` tokens (already done), and mask email-shaped substrings.
- Phone numbers inside free text are not pattern-masked: a digit pattern would also destroy ids, amounts, and timestamps. The protection there is the caller rule below.
- Escape U+2028, U+2029, U+0085, and the bidirectional control characters (U+202A to U+202E, U+2066 to U+2069) in the output line (SEC-007).

**Additions decided on 2026-10-11 after the first re-check (implemented in commit 28c92d1 and re-checked the same day; each names the finding that tracked it).**

- Keys, "equals" list, add: `username`, `customername`, `contactname`, `tel`, `mobile`. These are the names a developer is most likely to give a copy of `User.name` or a phone number (SEC-015).
- `key=value` and `key: value` pairs inside strings are also masked when the key **equals** `sid`, `pass`, `pin`, or `otp` (the short secret names of the "equals" list; the rest of that list stays key-only because words such as `name`, `query`, and `hash` are too common in ordinary text). A run of up to 32 blanks on either side of the separator, and the separator `=>`, must not defeat the mask (SEC-015).
- The local part of an email may contain an apostrophe (`o'brien@example.com` is accepted by `z.email()`, verified against the installed Zod); the email mask must cover the whole local part and today leaves `o'` (SEC-015).
- Local-scheme exemption (`file`, `node`, `webpack`, `webpack-internal`, `turbopack`): allowed, but it covers only that URL. A further `://` inside the same unbroken run of text must still have its user-info masked (SEC-012).
- File-position exemption: allowed only when the colon is followed by a line number and nothing else, that is digits, optionally `:` and more digits, and then the end of the text, a blank, a line end, or `)`. `session.ts:12:5` stays readable; `db.password.prod:9x7Qz` is masked (SEC-013).
- Clipping: a string is still clipped before it is scanned, so that the cost stays bounded, but the clip must not leave the beginning of something the full string would have masked. At a cut, an unfinished URL (a `://` with no blank after it) loses everything after `://`, and an unfinished email (an `@` in the last 256 characters with no complete domain after it) loses its local part (SEC-014).
- Output escaping is widened from the list above to: U+007F to U+009F (DEL and all C1 controls; U+009B starts a terminal escape sequence on terminals that honour 8-bit controls), U+2028, U+2029, and every character of Unicode general category Cf (format). Cf covers the soft hyphen U+00AD, the Arabic letter mark U+061C, U+180E, zero-width characters and direction marks U+200B to U+200F, all bidirectional controls, U+2060 to U+206F, the byte order mark U+FEFF, U+FFF9 to U+FFFB, and the tag characters U+E0001 and U+E0020 to U+E007F. In a regular expression with the `u` flag this is `[\u007F-\u009F\u2028\u2029\p{Cf}]`; a character outside the Basic Multilingual Plane is written as its two `\uXXXX` surrogate escapes. A JSON parser reads back exactly the original string, so nothing is lost for machines (SEC-016).

**What callers must do (every agent that writes a log line).** Log identifiers and outcomes, not payloads. Never pass a request body, a `Request`, a `Headers` object, a database row, or user-typed text to the logger. Database-layer errors are logged with their class name, code, and target model or constraint only; the message of a query-validation error is not logged, because it embeds the query arguments (to be confirmed by the database agent against the installed Prisma version in T-013). Rate-limit keys are never logged, since they contain an email or an address. Key-based redaction is a second line of defence, not the control.

**Lines that a security rule requires are not subject to `LOG_LEVEL` (decided 2026-10-12, seventh round; SEC-031).** Since commit b40abf0 the validated `LOG_LEVEL` reaches every logger of the process, so `LOG_LEVEL=error`, which `src/server/env.ts` accepts in production, removes every line below `error`. Three kinds of line are required by a rule of this document, and all three are below `error`, because nothing a client can cause at will may be logged at `error` (SR-05 item 10): the start-up warning of SR-01, the saturation warning of SR-02 item 4, and the security events listed above (a rate-limit refusal, a failed or successful sign-in, a sign-up, an `Origin` check failure, an admin action). Rule: these lines are written whatever level is configured. `LOG_LEVEL` chooses how much diagnostic output there is; it does not choose whether a security event is recorded. The mechanism is backend-api's to design with devops. Two are acceptable: a method of the logger that the level does not filter, used for exactly these lines; or `src/server/env.ts` refusing in production any level above the one these lines are written at, with every one of them written at that level. The first is preferred, because it keeps `warn` meaning a warning.

The mechanism chosen (commit f66ab8c, SEC-031, re-checked 2026-10-12) is the logger method **`security(level, message, fields?)`** of `src/server/logger.ts`, on the process-wide `logger`, on every logger `createLogger` makes, and on every child of either. It writes at `info`, `warn`, or `error` whatever level is configured; any other level value (possible only from untyped code) is written as `warn`, never dropped. It is the same line as every other: the same redaction, scrubbing, and escaping, and `level`, `timestamp`, `message`, and a bound `requestId` cannot be replaced through `fields` (tested). On a logger without a bound request id, a `requestId` field is written as the caller gives it (by reading; the same for every method), so callers set the request id only through `child({ requestId })`. Rules for callers: (1) every line that a rule of this document requires, and only those, is written with `security()`: the SR-01 start-up warning, the SR-02 saturation warning, and each security event listed above; (2) no other line uses it, because it bypasses the operator's choice of volume; (3) it carries the same data limits as any line: ids, outcomes, a rule name, `clientIp` and a truncated `User-Agent` on security events only, never a key, subject, email, or payload; (4) a security event that a client can cause at will (a failed sign-in, an `Origin` failure) is written at `warn` or `info`, never `error` (SR-05 item 10), and is bounded by the rate limit that counts it, not by `LOG_LEVEL`. A consumer that accepts the narrow `Logger` interface has no `security()`; code that writes a required line takes `StructuredLogger`. The line carries no marker that tells it apart from an ordinary line of the same level; if operators need to select security lines, a fixed field set after the caller's fields (as `level` is) is the way, not a field a caller passes.

State today: the saturation warning uses `security("warn", ...)` (SEC-031 fixed); the SR-01 warning in `src/server/env.ts` still uses `warn` and is safe only by the order of `loadEnvAtStartup` (the level is applied after it), handed to devops to move to `security()`; no code writes a security event yet. The rule must hold before T-015 writes the first sign-in event. Not required at every level: the line for a body that broke off (SR-05 item 10 says "at most") and the recovery line of the health check. The outage line of the health check is at `error` and is always written.

### SR-05 Request body size (decided 2026-10-11)

**Is a limit a security requirement? Yes.** Reading a body means holding all of it in memory, and for JSON holding it twice (the text and the parsed value). When this rule was decided, the handler pattern written in `src/server/http.ts` read the body before the actor was known, so the cost was available to anyone who could reach a mutation endpoint, signed in or not. (D-031 point 4 and item 5 below changed that order, and the pattern in the file follows it since 2026-10-12. The limit stays a requirement under the new order, because the endpoints that take a body from an anonymous caller remain.) A single process serves the whole site; a handful of concurrent requests of a few hundred megabytes each end it. The number is a technical security decision; an endpoint that needs more than the default states so in its contract.

**Rule.**

1. No handler calls `request.json()`, `request.text()`, `request.formData()`, `request.arrayBuffer()`, or `request.blob()` itself. Bodies are read only through helpers in `src/server/http.ts` (JSON) and the upload module (multipart), and every such helper enforces a limit in bytes.
2. JSON bodies: the default limit is **100 KiB (102,400 bytes)**. An endpoint may ask for more, up to **1 MiB (1,048,576 bytes)**, by passing the limit explicitly; its entry in `docs/API_CONTRACTS.md` then states the limit. Nothing above 1 MiB is JSON.
3. Enforcement has two steps, and both are required. First, when `Content-Length` is present, is not a plain decimal number, or exceeds the limit, the request is refused before any of the body is read. Second, the body is read as a stream with a running byte count and reading stops as soon as the count passes the limit, because `Content-Length` can be absent (chunked transfer) or untrue.
4. A body over the limit is `413 PAYLOAD_TOO_LARGE` with the generic message and empty details. It is an ordinary client error: not logged at error level, and nothing of the body is kept.
5. (Rewritten 2026-10-11 after D-031 point 4. The earlier wording, "origin check, content-type check, size-limited read, schema validation", placed neither identity, nor role, nor the rate limit, and is withdrawn.) **The order of checks in a handler** is the ten steps of `docs/API_CONTRACTS.md` section 1.8. The step numbers below are that section's numbers. The first check that fails gives the answer and no later check is made. The two documents say the same thing: the one place where they differed, the store status at steps 4 and 8, was settled by D-032 point 1 and is in section 1.8 since 2026-10-12 (the table was compared step by step on that day). If they are ever read differently anywhere, that is a defect to report, and until it is settled the reading that reads less of the body and tells the caller less is the binding one.

   | Step | Check | Refusal | Reads the body | Security ruling |
   | --- | --- | --- | --- | --- |
   | 1 | Mutations: `Origin` equals the application origin (TM-16) | `403 FORBIDDEN` | No | **Approved.** It must come before identity. The answer then depends only on a header the caller wrote, so it is the same whether or not the browser holds a session: a foreign page cannot use the status to learn that its visitor is signed in, the session is not looked up for a cross-site request at all, and no cross-site request reaches the code that acts on a cookie. `403` instead of `401` for an anonymous cross-site mutation tells the caller nothing it did not send itself |
   | 2 | Mutations: the one accepted `Content-Type`, also when there is no body (TM-16) | `415 UNSUPPORTED_MEDIA_TYPE` | No | **Approved**, for the same reason: the answer depends only on the caller's own header. This is the check that still stops a plain HTML form where an old browser omits `Origin`, so it also has to come before anything acts on the session |
   | 3 | Identity, on anything but a `public` endpoint: a valid session whose user is active, both read from the database in this request (TM-02, TM-26) | `401 UNAUTHENTICATED` | No | **Approved.** A deactivated user is answered exactly like a caller with no session |
   | 4 | Access level of the endpoint, from the caller's role and, **for the access level `seller`, the status of the caller's store**, both as read from the database at step 3 (TM-07, TM-26) | Wrong role: `403 FORBIDDEN`. Right role, store `SUSPENDED`, access level `seller`: `403 SELLER_NOT_APPROVED` | No | **Approved** (D-032 point 1; section 1.8 states it this way since 2026-10-12). See "Store status" below |
   | 5 | Rate limit, on the endpoints that have one (TM-01, TM-30) | `429 RATE_LIMITED` | No | **Approved**, with the guarantees under "Rate limit" below written into the contract |
   | 6 | The body is read through the size-limited helper (items 1 to 4, 8, and 9; TM-33) | `413 PAYLOAD_TOO_LARGE` | Yes | **Approved.** `413` before `400` is the only possible order: what is refused unread cannot be validated. A request that is too large and also invalid in a header or a path parameter is `413` |
   | 7 | Validation of the body, path parameters, query, and required headers | `400 VALIDATION_ERROR` | Yes | **Approved**, with one sentence to add to the contract: validation looks at the request only and makes no database query, so a `400` can never depend on whether something exists |
   | 8 | In the service: the store status again, by the service's own check and by the guarded statement (DATA_MODEL.md section 7.7) | `403 SELLER_NOT_APPROVED` | | **Approved** together with step 4 (D-032 point 1): this is the authoritative check (CLAUDE.md rule 2), and it is not the first place a suspended store is refused |
   | 9 | In the service: the resource does not exist, or is another user's or another store's (TM-05, TM-06; D-015) | `404 NOT_FOUND` | | **Approved.** See "Enumeration" below |
   | 10 | In the service: every other outcome | `409`, `422` | | **Approved**, on the condition that it never comes before step 9 for a resource named by an id |

   **Store status (steps 4 and 8): the one rule.** `requireActor` loads the user's active flag, the role, the store id, and the store status from the database on every request (TM-26; that is what "the first check" in DATA_MODEL.md section 7.7 means: the first read, at step 3). What is refused with them is decided by the access level of the endpoint, and it is decided at step 4, before the rate limit and before the body. For the access level `seller` that includes the store status; for `seller (any store status)` it is the role alone. The role is judged first, so a customer on a seller endpoint is still `403 FORBIDDEN`. The handler does this with pure helpers on the `Actor` (D-022): the role helper stays a role-only check, which is what backend-api asked for, and a second helper judges the store status; an endpoint of access level `seller` calls both. The service repeats the check and the write carries the condition itself, because a suspension can commit between step 4 and the write; a refusal there has the same code. The early check is a refusal made sooner, never the control. Reasons:
   - D-031 point 4 states the principle: the server does not read a body for a caller it will refuse. Whether a suspended seller will be refused on a `seller` endpoint is known at step 3 from data that was already read. Section 1.8 as first written read the body anyway, and for `POST /seller/uploads` that is a multipart body of up to 5 MB from the one kind of account an admin has just sanctioned (TM-17, TM-33).
   - Nothing of an upload may reach storage before the caller is known to be allowed. With the store status at step 8, the handler has to hold or store the file before the service refuses it; with it at step 4 the question does not arise.
   - The access table of section 1.8 already defines `seller` as "role `SELLER` and the store `APPROVED`". A step named after the access level that checks half of it is how a handler ends up with the wrong half.
   - One order for every `seller` endpoint, JSON or multipart. The security need is the upload; the rule is general because two orders for one access level is a mistake waiting for the next endpoint. The visible difference: a suspended seller who sends an invalid body to a `seller` endpoint is answered `403 SELLER_NOT_APPROVED`, not `400`.
   - It leaks nothing: the only caller who can receive `SELLER_NOT_APPROVED` is the owner of that store, who reads the same status from `GET /seller/store`.

   This differed from the literal text of D-031 point 4 ("then the store-state and ownership checks inside the service"). The orchestrator amended that point in D-032 point 1, and section 1.8 of the contract states steps 4 and 8 as above since 2026-10-12. The condition on the upload endpoint stands as a rule for T-041: a handler that reads a multipart body before the store status is judged would be registered as a finding (TM-17, TM-33).

   **Rate limit (step 5): what the contract must guarantee.**
   - A request that reaches step 5 uses one allowance whatever happens to it afterwards (`413`, `400`, `403`, `404`, `409`, or success). Otherwise every later refusal would be a free probe and a free body read.
   - Requests refused at steps 1 to 4 use none. That is safe: none of those steps reads a body, and none answers a question about anything but the caller's own headers and session. The only secret they touch is the session token, which is not guessable (T-015 states its length and source). What such a request costs is at most the session lookup, the same as any `GET`, and the application does not bound it (residual risks). A request with no session cookie must not cost a database query.
   - A per-user subject is `actor.userId` from step 3 and nothing else (SR-01).
   - **Endpoints that take a body from an anonymous caller (sign-up, sign-in).** The per-address rule (`sign-up`, `sign-in-address`) is consumed at step 5 by every request that passed steps 1 and 2, before a byte of the body is read and whatever the outcome. One address therefore causes at most 5 body reads and 5 password checks a minute at sign-in and at most 5 body reads and 5 password hashes an hour at sign-up; these numbers are the bound on body reads and on credential guessing from one address, and with the default proxy configuration they are the bound for the whole site (SR-01).
   - The body of these endpoints is read under the default limit of item 2, also when it is the auth library that parses it: either the wrapper reads it through the helper and hands it on, or T-015 shows the library's own bound (item 1 has no exception for the library).
   - **The per-email rule of sign-in** (`sign-in-email`) cannot be at step 5, because the email is in the body. Its place is fixed: after the per-address rule allowed the request (SR-01), after the body was read and the email validated and normalised, and **before the password is looked at**. Under concurrent requests no more than the limit of password checks may happen for one email in one window. Its refusal is the same `429` and does not say which rule refused. It is counted on the email as typed, in the same way whether or not an account has that email (TM-03). A request it refuses has already used a per-address allowance and does not get it back.
   - T-015 lists every route of the auth library that checks a password or creates an account, and shows both rules on each; a second route that verifies a credential without them would bypass all of the above (TM-01).

   **Enumeration (steps 7 to 10; D-015, TM-03, TM-05, TM-06).** Checked on 2026-10-11 against section 1.8 and the endpoint entries, on paper: with the order above no step tells a caller that a resource exists but is not theirs, that another seller's store is suspended, or which condition hides a product. That holds only while these stay true, and each is a requirement:
   - Steps 1 to 7 never consult the resource. An id in a path or a body is checked for its form only.
   - Ownership is part of the query (`WHERE id = ... AND userId or storeId = ...`), not a fetch followed by a comparison, so a foreign id and an unknown id take the same path and get the same `404`, message, and `details.resource`.
   - No outcome of step 10 that depends on the state of a resource (`INVALID_STATE_TRANSITION`, `UPLOAD_IN_USE`, `PRODUCT_UNAVAILABLE`, and the like) is evaluated for a resource that is not the caller's.
   - Step 8, where it applies, comes before step 9: a suspended seller is refused the same way for every id and cannot probe ids at all.
   - The cart (section 5.4): `PATCH /cart/items/{itemId}` answers `409 PRODUCT_UNAVAILABLE` with `reason: "NOT_AVAILABLE"` only for the caller's own line, after the ownership check; another user's line is `404` whatever its product. The caller already reads `unbuyableReason: "NOT_AVAILABLE"` for that line from `GET /cart`, so the `409` says nothing new, and it must stay that way: no price, no stock, no reason beyond that one value, and the same answer when the hidden product is also out of stock. `POST /cart/items` names a product, not a line, and stays `404` for a hidden product, so a caller without a line cannot tell a hidden product from one that never existed. The two answers are consistent and are approved.

   Not part of the order and still open for T-015: that sign-in answers a deactivated account, an unknown email, and a wrong password identically, and what sign-up answers for an email that is already registered (TM-03).
6. Uploads keep the limits of "Upload policy" (5 MB per file, 8 files), enforced in the same streaming way by the upload task; the total accepted for one upload request is at most 41 MiB.
7. A body limit at the reverse proxy is welcome as an outer layer (devops, `docs/DEPLOYMENT.md`) but is not the control: the application must be safe when reached directly, as in local development and tests.
8. (Added 2026-10-11 after the re-check, SEC-020.) The memory a helper holds while it reads must be in proportion to the limit, not to the number of chunks the body arrives in. The bytes are copied into one buffer that never grows past the limit; the chunk objects themselves are not kept. A chunk with no bytes is not kept either. A chunk that is not bytes (anything other than a `Uint8Array`) is refused as a server fault at once, because it cannot be counted. The refusal of an oversized body does not wait for the source to confirm the cancellation. The same holds for the upload reader when it is written.
9. (Added 2026-10-11 after the re-check of the SEC-020 fix, SEC-021; reworded the same day at the re-check of the SEC-021 fix, when the number was decided.) A read must end.
   - **Empty chunks.** One body may contain at most **200,000** chunks with no bytes (`MAX_EMPTY_BODY_CHUNKS` in `src/server/http.ts`). The number is the same for every call, whatever its byte limit. The chunks are counted over the whole body: bytes that arrive in between do not start the count again. The 200,001st empty chunk is refused at once as a server fault (a `TypeError`, so a 500), the cancellation is started and not awaited, and nothing more is read.
   - **The length that is counted.** The byte count uses the length the chunk really has, taken through the built-in typed-array getter, never the `byteLength` or `length` the chunk object itself reports. The count and the copy therefore always agree, and a chunk cannot switch the limit off by what it says about itself. An object that passes for bytes without being a typed array is a server fault.
   - **What follows.** One body is never read in more than its byte limit plus 200,000 plus 2 reads.
   - **Changing the number** is a change of this rule: it is decided here first, and a security test pins the value. It may be lowered only together with the security agent, because a regression test of SEC-020 sends exactly 200,000 empty chunks and must stay as it is.
   - The same holds for the upload reader when it is written, with a number of its own stated here.

   **Reason for the number, and a correction.** The first wording of this item said that any allowance "up to the byte limit" was acceptable. That was wrong on its own evidence: the default byte limit is 102,400, and the SEC-020 reproduction written earlier by the security agent requires a body with 200,000 empty chunks to be accepted, while the SEC-021 reproduction accepts a refusal anywhere up to twice the default limit (204,800 reads). The tests are the binding statement and neither body was changed; the wording was. 200,000 is acceptable for three reasons. It is a constant, so the bound on the reads of one body is known. It costs nothing in memory (0.10 MB held for the full allowance). And it is not the most a body may already cost in reads: a body at the 1 MiB ceiling may arrive as 1,048,576 chunks of one byte, five times as many reads, and that cannot be refused because those chunks are the body. Measured on 2026-10-11 with a source that answers every read without yielding: 200,000 empty chunks take 73 to 87 ms, 102,400 one-byte chunks 44 to 47 ms, and 1,048,576 one-byte chunks 328 to 349 ms; in each case no timer fires until the read ends, because the reader does not yield either. That hold is bounded and accepted (residual risks); a yield every few thousand chunks would remove it and is not required.

10. (Added 2026-10-11, code-review finding CR-05; SEC-024.) **A body that stops arriving is the client's doing, not a server error.** When the source of a body fails while it is read (the connection breaks, the request is aborted, the body ends before its declared length), the request is answered as a client error (a status below 500; nobody is left to receive it) and is logged at `warn` level at most: one line, a fixed message, the error's class name and code, no stack, nothing of the part that was read, and no `clientIp`, because it is not one of the security events of SR-04. The reader's own refusals stay server faults at `error` level: a chunk that is not bytes (item 8) and the empty-chunk allowance (item 9). An error thrown by the source's read cannot be attributed with certainty, so all of them are treated as the client's; a real fault of the framework in that place is then seen at `warn`, which is accepted. The general rule behind it: **nothing a client can cause at will is logged at `error` level.** Error-level lines are what operators alert on (TM-32), and a line with a stack per request is also the cheapest way to fill a log. This corrects the earlier position of this document: the SEC-019 re-check recorded "a 500 through `errorResponse`" for a broken-off body as correct and listed the log line only as a residual risk. The same holds for the upload reader when it is written.
11. (Added 2026-10-11, code-review finding CR-03; SEC-022.) **Bytes that are not valid UTF-8 are refused, never repaired.** A JSON body is decoded strictly (`TextDecoder` with `fatal: true`, or the equivalent). A body with an invalid byte sequence is `400 VALIDATION_ERROR` with `invalid_json`, exactly as a body that does not parse, with nothing echoed and nothing logged (`docs/API_CONTRACTS.md` section 1.1 already says so). Reason: a lenient decoder replaces each invalid sequence by U+FFFD, so the server validates and stores a text the client did not send, two different bodies become the same value, and a proxy or filter in front of the application that reads the bytes differently sees another request than the application does. A leading byte order mark stays accepted and removed.

    (Extended 2026-10-12, SEC-028, after the orchestrator ruled where it is refused.) **The same holds for text that arrives through an escape.** The bytes of a body are strict UTF-8 and cannot carry half of a surrogate pair, but `"\ud83d"` is valid JSON in plain ASCII. A JSON string that is not well-formed Unicode, as a value or as an object key, at the root or at any depth, is refused in `readJsonBody` as `400 VALIDATION_ERROR`, never repaired and never handed out, with nothing echoed and nothing logged. The field error stands at the root (`path` `""`), and that is accepted: a path to the string would repeat keys of the body, and may run through a key that is itself such a string. Its field code is provisional with item 8.2-12 of the contract. A complete pair written as two escapes is ordinary text. The walk that looks for such a string must cost time in proportion to the size of the document (a security test bounds it for the largest documents of each shape); it sees a value of at most 32 levels (item 12), so its stack depth is bounded whether or not it recurses. Not covered, on purpose: U+0000, noncharacters, and unassigned code points are well-formed and are handed out. A PostgreSQL text column cannot hold U+0000, so the shared string type of the schemas must refuse it, or a client can turn any text field into a 500 with an error-level line; that is a requirement on the first schema (backend-api), not verified against the database in this review.
12. (Added 2026-10-11, code-review finding CR-04; SEC-023.) **A JSON body may nest arrays and objects at most 32 levels deep.** A deeper body is refused in `readJsonBody` as `400 VALIDATION_ERROR`, with nothing echoed and nothing logged; the field code is backend-api's to choose and to write into `docs/API_CONTRACTS.md` section 1.1. The check itself must not recurse and must cost time in proportion to the length of the body. Reason: the byte limit bounds the size of a body, not its shape. 102,400 bytes hold about 51,200 nested arrays and 1 MiB about 524,288; the parser accepts both (verified in the SEC-019 re-check). Anything that later walks such a value by recursion (a recursive or pass-through schema, a copy, a serialiser for a JSON column) overflows the stack, which is a 500 with an error-level line and a stack per request, from any caller who can send a body. No such walk exists today, because no schema exists; the limit belongs in the one helper so that no future schema has to be safe by convention. The number is a technical decision of the security owner: the bodies in the contract nest a few levels at most (an object holding an array of strings is the usual shape), and 32 is far below anything a stack notices. Changing it is a change of this rule. Schemas stay strict objects in any case (TM-04, TM-27); a schema that accepts an arbitrary nested value needs a reason recorded here.

**Reason for item 8.** The sender chooses the chunk sizes: over HTTP a body can be sent as chunks of one byte each, and each chunk reaches the reader as a separate object of about 240 bytes. Measured on 2026-10-11, a 102,400-byte body sent that way holds about 24 MB while it is being read and a 1 MiB body about 245 MB, and the sender can pause before the last byte to keep it held. The sentence below about the worst case per request is true only with item 8 in place.

**Reason for the numbers.** The largest JSON bodies in the requirements are a product with its description and a checkout with an address; both are a few kilobytes, and 100 KiB leaves more than an order of magnitude of room, including for Thai text at three bytes a character. 1 MiB as the ceiling keeps the worst case per request small enough that the rate limits, not memory, are what bounds an attacker.

**Status.** Items 2 to 4 are implemented in `readJsonBody` and were re-checked on 2026-10-11 (SEC-019 fixed). Item 8 is implemented in `readBytesUpTo` and was re-checked on 2026-10-11 (SEC-020 fixed); the measurements in "Reason for item 8" are those taken before that fix. Item 9 is implemented in `readBytesUpTo` (`MAX_EMPTY_BODY_CHUNKS`, `realByteLength`) and was re-checked on 2026-10-11 (SEC-021 fixed). Items 1 and 5 are caller rules and cannot be checked until a handler reads a body. The handler pattern in the file comment of `src/server/http.ts` shows the ten steps of item 5 since 2026-10-12 (code-review finding CR-09); it was re-checked that day against section 1.8 of the contract, and a security test compares the two, but it is a comment: nothing applies it and nothing enforces it, and the names of the two helpers of step 4 are placeholders until T-015. For item 1 a security test checks that no `route.ts` under `src/app` reads a body by itself; the only handler so far is the health endpoint, which reads none. Item 6 belongs to the upload task; item 7 to deployment. Items 10, 11, and 12 are implemented in `readJsonBody`, `readBytesUpTo`, and `errorResponse` and were re-checked on 2026-10-12 (SEC-024, SEC-022, SEC-023 fixed). ### SR-06 Server log retention and access (owner decisions of 2026-10-11: D-025 OQ-21; D-026 OQ-47 and OQ-48)

**Rule.** Server logs are kept for at most 90 days and are then deleted, in every copy. Only system administrators may read them, and "system administrators" are only the named people who operate the servers. This is a security and privacy requirement, because security log lines contain the visitor's IP address (SR-04), which is personal data.

What it means for this project:

1. "Server logs" is every stored copy of what the application writes through `src/server/logger.ts`, and every other log of the same deployment that records a visitor's address or request, in particular the reverse proxy's access log. It includes log files on disk, the host's log collector, any error-tracking or monitoring service that receives log lines, and exports and backups of any of these. The owner confirmed that the 90 days cover every copy, log backups included (D-026, OQ-48). A copy kept longer than 90 days anywhere breaks the rule, with the one exception of item 8.
2. Deletion after 90 days is automatic. It is not a task someone has to remember. **90 days is a maximum, not a promise that logs are available that long** (D-026, OQ-48): a deployment that keeps logs for a shorter time, or loses them at a release, does not break this rule. How long logs must at least be kept to be useful for investigating an incident is therefore not set by the owner's answer; if a minimum is wanted it is a new decision.
3. "System administrators" are only the named people who operate the servers (D-026, OQ-47). The application's `ADMIN` role is a shop role and gives no access to server logs; neither does being a seller or support staff. Access is given to named individual accounts, not to a shared account and not to a role of the application, and the list of those accounts is part of the deployment evidence.
4. The application offers no way to read server logs: no page, endpoint, download, or admin screen shows log lines. Adding one would be a new decision recorded here.
5. The rule covers logs only. The database audit log (`AuditLog`) is a business record with its own retention ("Privacy and data retention") and holds no IP address in the draft data model; it must stay that way, or it falls under a retention rule of its own.
6. SR-04 is unchanged and comes first: 90 days is how long the permitted content is kept, not a licence to log more. The IP address appears only under `clientIp` and only on the security events SR-04 lists.
7. Local development is outside the rule as long as it handles no real visitor data.
8. **The one exception: an open security investigation** (D-026, OQ-48). Log lines that are evidence in an open security investigation may be kept past 90 days until the investigation is closed. The owner set three conditions, and all three must hold: only the relevant lines are kept, not the whole log or a whole day of it; there is a written record of what is kept and why; and the lines are kept only until the investigation is closed. What that means in practice, set here by the security owner as the least that makes the conditions checkable: the record is written when the lines are set aside, not afterwards, and names the investigation, the lines or the selection that produced them, the reason, who set them aside, and the date; the lines that are set aside stay under the same access rule as the logs (item 3) and the same content rule (SR-04); and when the investigation is closed they are deleted and the record says when. An investigation that is not about security (a customer dispute, a performance problem) is not covered by the exception. (Added 2026-10-11, for DEPLOYMENT.md DEP-Q5.) One more minimum of the same kind: every open hold is looked at again at a fixed interval, and each look is added to the record with its date, who looked, and whether the investigation is still open. Without it nobody can show that the lines are still evidence in an open investigation, and "until it is closed" becomes "for ever" by neglect (TM-34). How often is the owner's to say (DEP-Q5; devops recommends every 30 days, and the security agent agrees). Whatever the answer, and until there is one, the interval is not longer than 90 days, the period the hold is an exception to; a hold with no recorded look for more than 90 days is treated as a breach of this rule.

**Who does what.** Enforcing retention and access is an operations task, not application code: devops implements and proves it in `docs/DEPLOYMENT.md` and the T-071 runbook once a hosting provider is chosen (the configured retention period of the logs and of their backups shown, the named accounts that can read logs listed, the procedure and the place of the record for item 8 described). The security agent reviews that evidence before a production release. **Nothing implements or verifies this rule today:** no hosting provider is chosen and no log collector exists.

**What the owner's answers settled.** The three questions the first version of this rule left open are answered by D-026: who "system administrators" are (OQ-47, item 3), whether 90 days is a promise of availability (OQ-48: it is not, item 2), and what happens to evidence of an incident still open on day 90 (OQ-48, item 8). Not said by the owner and not decided here: who may open and close an investigation hold. Until someone is named, it is the system administrators of item 3, and the record of item 8 is what makes their decision reviewable.

### SR-07 IP address and browser details stored with a session (owner decisions of 2026-10-11: D-025 OQ-22; D-026 OQ-49 and OQ-50; D-027)

**Rule.** The session record may hold the IP address and the browser details (the `User-Agent` header) of the sign-in that created it. Both are deleted when the session ends or expires; for a session that expires they must be gone within one day of the expiry. Database backups, which hold a copy of them, are kept 30 days. This is a requirement on the auth task (T-015) and, for the backups, on deployment.

What it means for T-015:

1. **What may be stored.** Exactly these two values, with the session. No other description of the device or the person: no fingerprint, no location derived from the address, no list of past addresses.
2. **Where the address comes from.** Only from `getClientAddress` (SR-01), so it is an IPv4 address, an IPv6 /64 network, or absent. When SR-01 gives `unknown`, nothing is stored. The auth library must not fill the field from `X-Forwarded-For` or any other header by itself (already required by SR-01, review item V10).
3. **Bound on the browser details.** The `User-Agent` is client-written text of any length and content. It is stored cut to at most 512 characters, is never interpreted on the server, and is rendered only as plain text (TM-15). This is a technical bound set by the security owner.
4. **"The session ends"** covers every way a session stops being valid: sign-out, revocation when a user is deactivated (REQ-A-02, TM-26), and any other revocation the auth task adds. At that moment the session record is deleted, or at the least its address and browser details are cleared in the same operation. Marking a session as revoked while the two values stay in the row does not meet the rule. Suspending a store is **not** one of these: it ends no session (D-027), so the sessions of a suspended store's owner, and the address and browser details in them, stay until sign-out, deactivation, or expiry like anyone else's.
5. **"The session expires"** means the same for a session nobody ended. An expired session must actually be removed, not merely ignored when its cookie is presented. An abandoned session (a closed browser, a lost phone) is never presented again, so removal cannot depend on the user coming back. **The bound is one day** (D-026, OQ-49): no session row that is more than one day past its expiry may still hold the address or the browser details. A clean-up that runs once a day is enough; one that runs only when the same user signs in again, or only when a request happens to arrive, is not, because a quiet day would break the bound. (Added 2026-10-11.) A technical margin on how the bound is met, which does not change the bound: runs exactly one day apart leave no room at all, since a session that expires just after a run waits a full day for the next one and a single late or failed run then breaks the bound unseen. The runs are therefore **at most 12 hours apart**, and one run happens when the application starts. The hourly run planned in `docs/DEPLOYMENT.md` ("Scheduled work") meets this.
6. **No copies.** The two values are not copied into any other table (orders, audit log, user profile), into a cache that outlives the session, or into a log line other than the security events of SR-04. The sign-in line in the server log keeps the address for 90 days under SR-06; that is the log's own rule and is intended, but it means the address of a sign-in is gone from the database when the session goes and from the logs up to 90 days later. Stated here so that nobody reads SR-07 as "the address disappears everywhere at sign-out".
7. **Who sees them.** No endpoint returns the address or browser details of a session to anyone other than the signed-in user it belongs to. Showing them to shop admins or sellers would be a new decision recorded here.
8. **Evidence expected from T-015.** Tests that show, against the database: after sign-out the record (or its two values) is gone; after deactivation every session of that user is gone; after a store suspension the owner's sessions are still there (D-027) and TM-26 holds all the same; a session past its expiry is removed by the chosen mechanism without the user returning, and the mechanism is shown to run at least once a day; with the default proxy configuration no address is stored; an over-long `User-Agent` is stored cut. The values actually configured (session lifetime, renewal, removal mechanism and how often it runs) are written under "Session and cookie settings".

**Open point for the auth task: how soon is settled, how is not.** The owner set the bound: one day after expiry, and a daily clean-up is enough (D-026, OQ-49). The mechanism is still not chosen. `docs/KNOWN_LIMITATIONS.md` records that the MVP has no background job runner and that nothing runs on a schedule, and whether the installed auth library deletes expired rows by itself, and when, has not been checked against the installed version. The session lifetime is not decided either. The security owner does not choose the mechanism here. T-015 must propose one that meets the bound on a day with no traffic at all. If it needs something that runs on a schedule, that is a request to the orchestrator and devops, not something the auth task works around silently; and a scheduled job that silently stops is a breach of the bound that nobody sees, so whatever runs the clean-up must make a missed run visible (a log line per run at the least).

**Database backups** (D-026, OQ-50). Backups are kept 30 days. A backup taken while a session existed still holds its address and browser details after the session is gone, until that backup is deleted; so the two values can exist in a backup for up to 30 days after the session ended or expired. That is the owner's decision and is intended; it is stated here so that nobody reads "gone within one day" as covering the backups. What follows for deployment (devops, `docs/DEPLOYMENT.md`): deletion of a backup after 30 days is automatic and covers every copy of it; a backup is readable only by the people of SR-06 item 3; a backup is stored encrypted and is encrypted on the way to where it is stored, and it is not kept only on the database host (a technical requirement of the security owner, added 2026-10-11: a backup holds every password hash and every address, outside the database's access control); and restoring a backup brings back session rows that had already been removed, so the restore procedure ends as "Restore" below says. Backups of logs are not database backups: they follow SR-06 and its 90 days. None of this is implemented: no backup exists.

**Restore** (security requirement, decided 2026-10-11; it replaces "the expired-session clean-up, and every session if the restore is the answer to a security incident" in the earlier wording of this rule, and it is stricter than that wording, not weaker). A restored database is the database of the day the backup was taken. Two things follow, and both bind the restore procedure in `docs/DEPLOYMENT.md` and the T-071 runbook.

1. **Every session is deleted at every restore, before the application serves a request.** Not only the expired ones, and not only after a security incident. The statement is `DELETE FROM "Session"`, and the check, which must return 0 before the application is started, is `SELECT count(*) FROM "Session"`. This contains the expired-session clean-up the owner required (D-028), so that answer is kept and exceeded. Reason: a session that was ended after the backup was taken (the user signed out, perhaps because the device was shared or lost, or the user was deactivated) is a valid session again in the restored database. Ending a session on the server is the control of TM-02 and TM-26 and the owner's decision D-027; a restore that brings ended sessions back undoes both without anyone deciding it, and nothing in a restored row says whether it had been ended. The expired-session clean-up does not touch such a row, because it has not expired. The cost is that every user signs in once more after an event that is rare, approved by a person, and already loses data. **This is a security requirement, not an owner preference**, so DEPLOYMENT.md DEP-Q7 is not a choice between two acceptable options: the owner is told the consequence (everyone signs in again after a restore), and serving from a restored database with its old sessions would have to be recorded in this document as an accepted risk with the owner as approver. The security agent would not recommend that in any circumstances. T-015 says whether any other table of the auth library holds something that works like a credential with a lifetime (`Verification`); if so, it is emptied in the same step.
2. **A restore does not lift a restriction.** Deleting sessions does not undo the other half of the problem: a user deactivated after the backup is active again in the restored database and can simply sign in, a store suspended after the backup is approved again, and a product taken down or rejected after the backup is on sale again (TM-26). Every user deactivation, store suspension, and product takedown or rejection that was in force just before the restore is in force again **before the application serves**, not repeated by an admin afterwards while the application is already open. How is for T-071, with these conditions. When the database that is being replaced can still be read (a rollback), the ids under each restriction are listed from it before it is overwritten; the list holds ids and statuses only, is reachable by the people of SR-06 item 3 only, and is deleted when the restore is finished. When it cannot be read (a loss), the admin-action lines of the server log are the only source (SR-04), and they may not reach back far enough, because logs have no minimum retention (SR-06 item 2); the record of the restore then says which period could not be reconstructed, and the shop admin is told before the application serves. Re-applying a restriction is written to the audit log like the admin action it repeats (TM-25).

Both hold for every database the application serves from, staging and a rehearsal with real data included. What a restore loses and cannot give back stays as DEPLOYMENT.md lists it (orders, and the audit log entries written since the backup).

### Position on the blind resend of a refused checkout (`docs/API_CONTRACTS.md` item 8.2-1; 2026-10-11)

**A position, not a ruling.** D-031 point 6 leaves the ruling to backend-api and security together, before T-032 starts. Nothing here is in effect.

- **Keeping the rule in the client only is not acceptable as the final state.** The rule is "the customer sees the lowered quantity and the new total before an order is placed for them" (D-026, OQ-30; BR-22). Today the only thing that keeps it is the page's script. A second tab with an older page, a retry made by a library, a service worker, or an intermediary that resends a request whose answer was lost each place the order unseen, and the server cannot tell that from the customer's confirmation. CLAUDE.md rule 2 makes the same point about hidden buttons: what only the page enforces is not a control. The harm is bounded, and that is why this is a position on a design and not a registered finding: the caller must hold the customer's own session, no other person gains anything, the quantity can only be lower than the one the customer chose, and the charge is computed by the server.
- **Preferred guard: a revision of the cart.** The cart carries a counter that goes up with every stored change of its lines, the lowering done by a refused checkout included. `GET /cart` and every cart and checkout answer return it; `POST /checkout` must send the value the customer was shown; inside the checkout transaction, under the cart lock that D-023 already takes, a value that is not the current one refuses the checkout and changes nothing. A blind resend carries the old value and is refused, because the refusal itself raised the counter.
- **Why this one of the three.** A stored refusal answers a repeat of the same key with the same refusal, which stops the exact resend but not a client that sends a fresh key on each try, and it adds rows that an account can create ten times a minute and that then need their own clean-up. A confirmation value does what the revision does, but only on the path after a refusal, and needs either storage or a signing key. The revision is one integer on a row that is already locked, needs no clean-up and no secret, and also covers a case the other two do not: a checkout sent from one tab after the cart was changed in another.
- **What no guard can do.** A client that reads the new revision and resends without showing anything still places the order. The server can make sure the client has received the new state, not that a person looked at it.
- **Conditions if it is adopted.** The revision is not an amount and not a secret; it is compared for equality only and never used for anything else. The idempotency lookup comes first, so a repeat of a checkout that succeeded still returns its order whatever revision it carries (TM-11). The refusal for a stale revision says only that the cart changed and returns the cart as `GET /cart` would.
- **Not covered by any of the three, stated so that nobody assumes it:** a price that the seller changed between the page the customer saw and the checkout. BR-18 makes the new price the one checkout uses. Whether the customer must also confirm a changed total is a product question for the owner, not part of 8.2-1.

### CSRF helper (`assertSameOrigin`, `assertContentType`, `readJsonBody`): review and decisions (2026-10-11)

First security review of the helpers added in commit 28c92d1, against TM-16.

| Point | Decision |
| --- | --- |
| The `Origin` header is compared as an exact string with the origin of `APP_URL`; the header is never parsed | Accepted, and the right design: nothing an attacker writes is interpreted. Browsers always send the origin in one canonical form (lower-case scheme and host, punycode for an internationalised host, no default port, no path), which is the form `new URL(APP_URL).origin` produces. Tested: 26 near misses are refused on every mutating method, among them an explicit `:443`, upper case, a trailing dot, a trailing slash, user-info, a look-alike suffix or prefix host, the other scheme, another port, `null`, an empty value, and repeated or combined values |
| A client that is not a browser and writes the origin differently (`https://shop.example:443`, upper case) is refused | Accepted. The API has no non-browser clients; fail-closed |
| A host name with a trailing dot is a different origin and is refused | Accepted. The deployment serves one canonical host and redirects any other spelling to it |
| `OPTIONS` and unknown methods are checked like mutations, so a cross-origin preflight gets 403 | Accepted and intended. The API is same-origin only and sends no CORS headers; a same-origin page never sends a preflight. Allowing any other origin would be a new decision recorded here, with an explicit allow-list and never a wildcard with credentials |
| `GET` and `HEAD` are exempt | Accepted, on the standing condition of TM-16 that they never change state. A handler that changes state on `GET` is a finding |
| An `APP_URL` that is not an absolute http or https URL throws `TypeError` on every call, including `GET` | Accepted: a broken configuration never passes a request. `src/server/env.ts` must reject the same values at startup (devops) |
| The content type must be exactly `application/json` (any letter case, parameters allowed); a missing, combined, or look-alike value is 415, decided before the body is read (tested: `bodyUsed` stays false) | Accepted. This is what keeps a plain HTML form, which can only send three content types, from reaching a JSON endpoint even where an old browser omits `Origin` |
| A body that is not JSON is 400 with a fixed message, no cause, and no log line | Accepted. The parser's message quotes the body, so dropping it is correct (tested: nothing of the body reaches the response or the log) |
| `__proto__` and `constructor` keys in a body | No pollution: `JSON.parse` creates them as ordinary own properties (tested). Schemas must stay strict objects so that such keys are rejected rather than carried into a service (TM-04, TM-27) |
| `trustsIncomingRequestId(config)` | Accepted. It is true exactly when SR-03 says so and false for every invalid configuration (tested with 14), so a broken configuration cannot make client-chosen request ids trusted |
| No body size limit (state at the first review) | Not accepted: SR-05, SEC-019. Fixed in commit e2a4a7a and re-checked 2026-10-11; what the re-check found is SEC-020, fixed and re-checked the same day; what that re-check found is SEC-021 (Low), fixed and re-checked the same day with nothing further found |

What these helpers do not cover, by design: they are opt-in per handler, they do not apply to the auth library's own routes (T-015 must show the library's equivalent checks), and the upload endpoint needs the same origin check with `multipart/form-data` (upload task).

## Session and cookie settings

Written by the auth agent on 2026-10-13 (T-015) from the configuration as built: `src/server/auth/auth.ts` (the Better Auth 1.7.7 options) and `src/server/auth/config.ts` (the constants). Each value below is asserted by a test named in brackets; "integration" means `tests/integration/auth/`, run against the test database. The security agent has not reviewed this section yet, and the status columns of TM-02, TM-03, TM-04, TM-19, TM-26, and TM-34 above are left for that review.

**Security review, 2026-10-13.** This section was checked against the code of commits 4bd5d96 to 7f3a767 and found accurate, with the exceptions registered as SEC-032 to SEC-036 (the per-email limit locks accounts out; bidirectional controls in names; `__Secure-` instead of `__Host-`; timing; `mysql2` in the production tree). The use of `security()` for the purge line is confirmed. The TM statuses above are updated. Details, commands, and evidence: [reviews/T-015-T-016-security.md](reviews/T-015-T-016-security.md).

**Library and what of it is used.** Better Auth 1.7.7 (`better-auth/minimal` with `better-auth/adapters/prisma`, transactions on). It hashes passwords (its default, scrypt; the stored form is `<salt hex>:<key hex>`), generates session tokens (32 random characters from `[A-Za-z0-9]`), and signs and verifies the session cookie (HMAC-SHA-256 with `AUTH_SECRET`). **Its HTTP handler is not mounted**: there is no `src/app/api/auth/**` route, so none of its own endpoints (update-user, change-password, reset-password, list-sessions, revoke-sessions, delete-user, get-session) is reachable [integration: "no route of the library is reachable"]. The application's routes under `src/app/api/v1/auth/` call it through `auth.api.*` after the checks of SR-05 item 5. Its own rate limiter is off (`rateLimit.enabled: false`), its IP detection is off (`advanced.ipAddress.disableIpTracking: true`), telemetry is off, and its log lines reach the application logger at `error` only (its `info` line for a duplicate sign-up contains the email).

**Cookie.**

| Setting | Value |

| Value | session token, `.`, HMAC signature (a token without a valid signature is refused [integration: forged cookies]) |
| `HttpOnly` | always |
| `Secure` | when `NODE_ENV=production` (`advanced.defaultCookieAttributes.secure`, set explicitly from the validated `NODE_ENV`, not inferred by the library); not in development and tests, which run on `http://localhost` |
| `SameSite` | `Lax` |
| `Path` | `/` |
| `Domain` | not set (host-only cookie) |

| Other cookies | none: the cookie cache (`session_data`) is off and `rememberMe` is always true, so no `dont_remember` cookie |

Asserted in a production-mode response [integration: "cookie attributes in a production-mode response", which builds the auth instance with secure cookies and an `https` origin and signs in and out through the sign-in and sign-out handlers]. **Not run:** a real `next start` with `NODE_ENV=production`, because production mode refuses the local databases by design (CR-49); the derivation `secureCookies = (NODE_ENV === "production")` is in `getAuth()` and is read, not tested against a running server.

**Session lifetime and renewal.** 7 days from sign-in, fixed (`session.expiresIn` 604,800 s). Not renewed while used (`disableSessionRefresh: true`) and refresh deferred to `POST` (`deferSessionRefresh: true`, and the library's `get-session` endpoint is not mounted), so **reading a session writes nothing**: no expiry update and no deletion of an expired row on read. That settles D-031 point 6 (X-07) for this project: a `GET` never writes, the library included [integration: "refuses an expired session, writes nothing while reading it"]. The cookie cache is off: the user, role, active flag, store id, and store status are read from the database on every request (TM-26) [integration: suspension and reinstatement take effect on the next request with the same session].

**Rotation.** Every sign-in creates a new session with a new token. When the sign-in request carries a valid session cookie, that session is deleted, so a browser ends with exactly one fresh session [integration: "rotates on login"]. A token chosen by a client is never accepted (tokens are generated by the library and signed).

**Response floor (SEC-035).** A failed sign-in and every sign-up answer take at least 250 ms plus a random 0 to 25 ms, counted from the start of the password step (`AUTH_RESPONSE_FLOOR`, `src/server/auth/config.ts`) [integration: "response floor (SEC-035, TM-03)"].

**What the session record stores (SR-07).** `token`, `userId`, `expiresAt`, `createdAt`, `updatedAt`, and, set in the library's `session.create.before` hook: `ipAddress` = the SR-01 result of `getClientAddress` (an IPv4 address or IPv6 /64 network), `NULL` when that is `unknown`, never a header the client wrote [integration: with no trusted proxy and a client `X-Forwarded-For`, `NULL`; with one trusted hop, the address one place from the right]; `userAgent` = the `User-Agent` header cut to 512 characters, never splitting a surrogate pair, `NULL` when absent [integration: 600 characters stored as 512].

**Ending a session.**

| Event | What happens | Evidence |
| --- | --- | --- |
| Sign-out (`POST /api/v1/auth/sign-out`) | The session row is deleted by the application (a failure is a 500, not a success: the library's own sign-out swallows a failed delete), then the cookie is cleared (`Max-Age=0`, same attributes) | integration: the old cookie is refused afterwards and the row count is 0 |
| Deactivation | `deleteSessionsOfUser(userId, tx)` deletes every session of the user, in the transaction that sets `isActive = false` (to be called by the admin service, T-050/T-051). As a second line, `getActor` refuses an inactive user even if a session row survived, and the session hook refuses to create a session for an inactive user | integration: "deactivation" cases; the hook case fails when its check is removed |
| Store suspension | Nothing (D-027): the session stays, `requireApprovedSeller` refuses with `403 SELLER_NOT_APPROVED` | integration: "a suspended seller keeps the login" |
| Expiry | An expired session is refused when presented and removed by the purge below | integration and unit |

**Removal of expired sessions (SR-07 item 5).** `purgeExpiredSessions()` deletes every `Session` row with `expiresAt` in the past and every expired `Verification` row. `startSessionPurgeSchedule()` runs it once when the server starts and then every hour (`SESSION_PURGE_INTERVAL_MS`; SR-07 requires at most 12 hours), one schedule per process (`globalThis`, `Symbol.for("marketplace.auth.sessionPurgeSchedule")`), timer unref'd, no overlapping runs. `src/instrumentation.ts` starts it after the environment is validated, and not when `NODE_ENV=test`. Every run writes one line: `security("info", "Expired sessions removed", { removedCount, removedVerifications })`, which `LOG_LEVEL` does not filter so that a missed run stays visible, or `error` "Expired session removal failed" with the error's class name and code only. The `security()` path is used here for a line SR-07 requires, not for an SR-04 event; the security agent should confirm that use. **Not run:** the schedule inside a real `next start` or `next dev` over an hour; the unit tests use fake timers and a stand-in purge, the integration test calls the purge directly.

**`Verification` table (SR-07 "Restore").** It is the library's table for one-time tokens (email verification, password reset). Nothing in this application writes to it today (no email delivery, so no verification or recovery flow exists); its expired rows are purged with the sessions. If a recovery flow is ever added, its rows are credentials with a lifetime and must be emptied at a restore together with the sessions.

**Passwords.** 8 to 128 characters at sign-up, checked by the request schema and again by the library (`minPasswordLength`, `maxPasswordLength`); sign-in accepts 1 to 128 so that its answer never depends on the policy. No composition rule and no breached-password check.

**Registration and enumeration (TM-03).** Sign-up never signs in (`autoSignIn: false`). The library then answers an email that is already registered with the same response as a new one, after hashing the submitted password so that the time is alike; nothing is created or changed for the existing account [integration]. The route answers `200 { "data": { "accepted": true } }` in both cases, with no cookie. Sign-in answers an unknown email, a wrong password, and a deactivated account with the same `401 UNAUTHENTICATED` and message, and the library hashes the password for an unknown email too [integration: identical bodies]. **Residual:** without email verification an attacker can still learn that an address is registered by signing up with it and then trying to sign in with the password just chosen (it fails only when the address was taken); this costs one sign-up allowance (5 an hour per address) per probe. REQUIREMENTS REQ-C-01 ("creates a CUSTOMER and logs in"; "duplicate email gives a generic error") cannot hold together with identical answers; the conflict is reported to the orchestrator for the owner, and the sign-up page is expected to call sign-in right after a successful sign-up.

**Secret.** `AUTH_SECRET`, required in every environment, at least 32 characters, and in production not containing `not_a_secret` (the marker of `.env.example` values). There is no default. It is read by `readAuthSecret()` in `src/server/auth/config.ts` with the conventions of `src/server/env.ts` (name and rule, never the value) [unit]; **it is not yet validated at start-up** in `src/server/env.ts` and not yet in `.env.example` (devops, handed on). Without it the auth routes answer 500.

**Rate limits on the auth routes.** As the table of `docs/API_CONTRACTS.md` section 6, through `src/server/rate-limit.ts` only: `sign-up` per client address and `sign-in-address` before the body is read, `sign-in-email` on the normalised email after the body and before the password [integration: the 6th attempt is 429 even with a body that is not JSON; the per-email limit holds across addresses and counts unknown emails alike; requests refused for origin or content type use no allowance]. No password-reset route exists, so none is limited.

**Security events.** `sign-in` (succeeded at `info`, failed at `warn`), `sign-up` (`info`), `origin-refused` and `rate-limited` (`warn`), all through `security()`, with `clientIp`, the user agent cut to 200 characters, the route, the outcome, and on success the user id; never the email, password, token, or body [integration: canaries]. Events that come before any allowance (`origin-refused`, `rate-limited`) are throttled to one line per kind and rule per minute, carrying the count suppressed since the last line [unit]; the others are bounded by the rate limit that counts them.

**Post-login redirect (TM-19).** `safeRedirectPath()` in `src/server/auth/redirect.ts` accepts only a path that starts with one `/`, has no backslash, blank, or control character, and resolves to the same origin; anything else becomes `/` [unit, 30 cases]. `src/proxy.ts` uses it for the `next` parameter. No sign-in page exists yet (frontend).

**Proxy (`src/proxy.ts`).** Redirects a request for `/seller`, `/admin`, `/account`, or anything below them that carries no session cookie to `/login?next=...`. It tests only the presence of a cookie with the session cookie's name; it is not the security boundary (TM-07) [unit: matcher cases and redirect].

**Admin bootstrap (T-016, REQ-A-11, BR-26).** `pnpm admin:bootstrap` (`scripts/bootstrap-admin.ts`, logic in `src/modules/auth/bootstrap-admin.ts`) is the only way an `ADMIN` comes to exist. Input from the environment only (`ADMIN_BOOTSTRAP_EMAIL`, `ADMIN_BOOTSTRAP_PASSWORD`, optional `ADMIN_BOOTSTRAP_NAME`), never from argv, so the password stays out of shell history and the process list; no default. The password policy is the sign-up schema's (8 to 128 characters) [unit, integration]. The password is hashed with the library's own `hashPassword` (the same scrypt the instance uses) and the user id has the library's format, so the admin signs in through `POST /api/v1/auth/sign-in` [integration]. It only inserts (one `User`, one credential `Account`, one transaction); an email already an admin's is "no change" (exit 0), a customer's or seller's is refused (exit 3) with nothing changed, compared without regard to letter case [integration: whole-database snapshot before and after]. The output names the account by user id; never the password or the email, and a failure by error class and Prisma code only [unit]. No audit row is written: DATA_MODEL section 4.1 lists the rows a run inserts, and `AuditLog.actorId` needs an acting user.

**Password recovery.** Not implemented, because no email delivery exists (DECISIONS.md, "Pending decisions": email provider). No reset route is mounted and the library's reset endpoints are unreachable.

## Privacy and data retention

- Personal data collected: email, name, phone, shipping addresses, order history, the client IP address and browser details (`User-Agent`) in security log lines (SR-04), and the IP address and browser details of the sign-in in the session record (SR-07). Nothing else.
- No payment card data is collected or stored. The mock provider takes no card input.
- What may and may not be written to logs is defined in SR-04.
- Thailand's PDPA applies to a real launch: a privacy notice, a lawful basis, data-subject request handling, and a retention schedule are required and are **not** part of the MVP. Recorded in KNOWN_LIMITATIONS.md.
- Order and audit records are retained indefinitely in the MVP; deactivated accounts keep their order history. Neither holds an IP address or browser details (SR-06 item 5, SR-07 item 6).
- Server logs are kept at most 90 days and then deleted, in every copy including log backups, and only system administrators may read them: the named people who operate the servers, never the application's `ADMIN` role (owner decisions of 2026-10-11, D-025 OQ-21, D-026 OQ-47 and OQ-48; rule SR-06). 90 days is a maximum, not a promise that logs exist that long. Lines that are evidence in an open security investigation may be kept until it is closed, only the relevant lines and with a written record of what is kept and why (SR-06 item 8). Not implemented: it is a deployment task (T-071).
- The IP address and browser details of a sign-in may be stored with the session and are deleted when the session ends, and within one day of its expiry (owner decisions of 2026-10-11, D-025 OQ-22, D-026 OQ-49; rule SR-07). Not implemented: it is part of T-015, and the mechanism that removes expired sessions is an open point there.
- Database backups are kept 30 days (owner decision of 2026-10-11, D-026 OQ-50; rule SR-07). Not implemented: no backup exists.
- The rules together: after a session is gone, the address of its sign-in is still in the server log until that line is at most 90 days old, and in any database backup taken meanwhile until that backup is 30 days old.

Known and standing:

- In-process rate limiting does not protect a multi-instance or serverless deployment.
- The process-wide limiter trusts its `globalThis` slot (SEC-030, accepted 2026-10-12): code running in the server process can plant a table, edit counters, or put something malformed there, which is replaced by an empty table and resets every limit once. A client cannot reach the slot. Only the exported `rateLimiter` is shared; a limiter made with `createRateLimiter()` counts for its own module copy, so production code must not create its own (nothing enforces this; a lint rule or a test that greps for `createRateLimiter` outside tests would).
- `logger.security()` is not filtered by `LOG_LEVEL` (SR-04). Once T-015 writes a line per failed sign-in or `Origin` failure, the volume of those lines is bounded only by the rate limit that counts the event and by the proxy, not by the operator's level. Each such event must be behind a rate limit, and log storage sized for a flood (SR-06).
- A `security()` line looks like any other line of its level; nothing marks it for an alert rule (SR-04). Operators who alert on the saturation warning match its message, `Rate limit store saturated`.
- The limiter uses fixed windows: a client can make up to twice the limit across a window boundary (for example 10 sign-in attempts in two seconds, then none for a minute).
- The limiter fails closed (SR-02): a flood from very many distinct networks can make one rule refuse new subjects while it lasts. Upstream protection (proxy or CDN rate limiting) is needed for that and is not planned.
- A per-email sign-in limit lets anyone lock a known email out of signing in by sending five bad attempts a minute. As built (T-015) every attempt counts, from one address suffices, and admin accounts are reachable: registered as SEC-032 (open). Counting only failures would not remove the lock-out, because the attacker's attempts are failures.
- The sign-in and sign-up response floor (SEC-035, 250 ms plus 0 to 25 ms) hides the timing difference only while the library's work (scrypt, inserts) stays below it. Under load, when that work takes longer, nothing is added and the difference shows again; the per-address and per-email limits bound the number of samples. A successful sign-in is not padded. Measured on loopback only (re-check 2026-10-13), not through a proxy or under concurrent load.
- Names: the schema refuses format characters, line separators, and blank-looking names since the SEC-037 fix (re-checked 2026-10-13), but still accepts unassigned, private-use, and default-ignorable characters and variation selectors (SEC-039, open), and U+200B to U+200D anywhere (owner decision for Thai), so two names can differ invisibly; look-alike visible characters (confusables, for example Cyrillic letters in a Latin name) are still accepted. Every screen that shows a name must render it isolated (`<bdi>`, SEC-033 rendering part), and every later name field (store, address) must reuse the schema rule.
- The `__Host-` protection (SEC-034) depends on browsers applying the prefix rules; it was not tested in a browser. Padded cookie names that the library's parser would trim are dropped before the library reads cookies (SEC-038 fixed, re-checked 2026-10-13); this holds only while every hand-over of request headers to the library goes through `headersForAuthLibrary` (a static case in `tests/security/sec037-038-recheck.test.ts` checks the `auth.api` calls under `src`; it does not see a call written another way, such as a destructured `api`), and a later library version that parses cookies through another path would need the same filter. Whether any browser stores and sends a cookie name with a raw 0xA0 byte is still not tested; with the filter it no longer matters for the session cookie.
- Sessions last 7 days from sign-in with no idle timeout and no re-authentication before admin actions; a stolen admin cookie is usable for up to 7 days unless the admin signs out or is deactivated.
- The admin bootstrap writes no audit row (DATA_MODEL section 4.1); the only trace of an admin's creation is the script's output and the row's `createdAt`. The script loads `.env` when present, so a bootstrap password put there stays on disk.
- `AUTH_SECRET` is not validated at start-up yet (handed to devops); without it the auth routes answer 500 (fails closed). No rotation of the secret is supported: changing it ends every session.
- With the default proxy configuration all clients share one per-address bucket (SR-01). Correct limits in any deployment depend on `TRUSTED_PROXY_HOPS` or `TRUSTED_CLIENT_IP_HEADER` being set correctly and on the application port not being reachable around the proxy. A wrong hop count either trusts a client-written address or rate-limits the proxy itself.
- Carrier-grade NAT, offices, and campuses put many users behind one IPv4 address; they share a per-address allowance.
- One holder of an IPv6 /48 controls 65,536 /64 networks, more than the 40,000 windows of an anonymous rule, and can keep `sign-up` (about 11 requests a second) or `sign-in-address` (about 670 a second) refusing new networks. Nothing fails open and existing subjects are unaffected (SR-02, capacity split).
- Addresses that a proxy writes in an unusual form share a subject: hexadecimal IPv4-mapped addresses are `unknown`, written-out mapped addresses and loopback share the all-zero /64, and all NAT64 clients share one /64 (SR-01).
- Logger redaction is by key name and text pattern. A secret or personal value under an unlisted key, or inside free text in a shape the patterns do not know, is still written. The control is that callers log ids, not payloads (SR-04).
- Shapes the logger is known not to mask, observed on 2026-10-11 and accepted in SR-04: a bare JWT or other token with no key in front of it; a header name and its value as two separate array items; `user:password@host` without a scheme; a value on the line after its key; a lower-case standalone `basic` credential; `file://user:password@host`; emails without a dotted domain, with a quoted local part, an address literal, or a percent-encoded `@`; a key written in full-width letters; a boxed `String` object; personal data under a key that is on no list (for example `dob`, `nationalId`); a digits-only value after a dotted key that ends like a file extension (`user.pin:1234`); a comparison or other operator between key and value (`password == x`, `password != x`); a session cookie under a name that contains none of the listed words (`connect.sid`; the auth library's `better-auth.session_token` is covered); and the first characters of an email's local part when a clip falls in front of its `@`.
- Nothing forces a handler to call `assertSameOrigin`, `readJsonBody`, or the rate limiter: each is opt-in per handler. When route handlers exist, a test must enumerate every mutation route and prove the origin and content-type checks on each (TM-16).
- The origin check compares against one configured origin. A deployment reachable under two host names (for example with and without `www`) refuses mutations on the second one; it must redirect to the canonical host.
- While a JSON body is read it holds one buffer of at most the limit, and for the length of one copy, when that buffer grows, up to about twice the limit plus the chunk in hand (SEC-020, fixed). A chunk is in memory before the helper sees it, so its size is the runtime's and the proxy's to bound, not the helper's: one oversized chunk is refused after it has arrived.
- The body reader does not yield to the event loop by itself. A source that answers every read without yielding holds the loop until the read ends or is refused: at most the byte limit plus 200,002 reads (SR-05 item 9, SEC-021 fixed), measured at about 80 ms for the full allowance of empty chunks and about 340 ms for a 1 MiB body in one-byte chunks. A body that arrives from the network yields between chunks; whether the framework can hand a route handler a body that does not was not verified.
- An object that passes for bytes without being a typed array (a `Proxy` of a `Uint8Array`, an object with its prototype) is refused with the engine's error and without cancelling the source; a `Proxy` can also make the bytes check itself throw. Both are a 500 with nothing read afterwards and need code inside the server process (observation in SEC-021).
- A chunk made in another JavaScript realm is refused as a server fault even when it is bytes (the check is `instanceof Uint8Array`). It fails closed; if a runtime or framework delivers bodies that way, every request with a body answers 500 until the check is changed.
- The application sets no time limit on reading a body. A client that sends slowly, or stops, holds what it has sent (at most the limit) and one connection for as long as the server and the proxy allow. Request and header timeouts are deployment settings and are not chosen yet.
- The local database image is pinned by digest (SEC-008, fixed) and nothing updates the pin: no dependency bot exists until the CI task (T-070). Until then the image gets security updates only when someone follows "Updating the database image" in `docs/DEPLOYMENT.md`. Local development and tests only.
- A client that drops the connection in the middle of a body is answered as a client error and logged as one `warn` line without a stack (SR-05 item 10; SEC-024 fixed, re-checked on 2026-10-12 against `readJsonBody` and `errorResponse` directly). What remains: every such request still writes one line, so on an endpoint without a rate limit a signed-in account can write `warn` lines as fast as it opens connections; a real fault of the framework in that place is seen only at `warn` (accepted in SR-05 item 10); and whether, and with which error, the framework reports a dropped connection to a route handler was not verified, because no handler reads a body. If the framework fails the request before or outside the read, none of this applies and its own handling does.
- A body that ends early without the stream failing is judged as what arrived. For an object or an array that is always "not JSON"; a bare number cut short is another valid number (`123` becomes `12`). No endpoint accepts a bare scalar as its body, and schemas are strict objects (TM-04), so nothing follows from it today.
- The status and the code of a body that broke off, and the field code of a body nested too deep, are provisional until items 8.2-12 and 8.2-13 of the contract are ruled. Both reuse `invalid_json` today, so a client cannot tell the three cases apart by code, only by message. The security tests pin the status class and the two constants, so a ruling changes no security test.
- A JSON object with the same key twice is accepted and the last value wins (the behaviour of `JSON.parse`; known, not tested in this review). Anything in front of the application that reads the first value sees another request than the application acts on. Not refused; to be looked at with the first proxy or filter that inspects bodies.
- The refusal of the local placeholder passwords (SEC-009) is a guard against a copied file, not a control against intent. It applies only when `NODE_ENV=production`, so a deployed host that runs `next dev` is not refused. It runs when the application starts: the Prisma CLI, the seed, and other scripts read `DATABASE_URL` without it, and the database client reads the variable itself until code-review finding CR-23 moves it to `readDatabaseUrl`. `docker-compose.yml` still falls back to the published passwords for local use, bound to 127.0.0.1. An encoded spelling and `PGPASSWORD` are refused since commit b123ef9 (SEC-025, fixed). Still outside it: the framework does not call the start-up hook when `NEXT_PHASE=phase-production-build` is in the server's environment, and then nothing is validated at all (SEC-029, open); a password file (`PGPASSFILE`, `~/.pgpass`), which the driver reads when neither the URL nor `PGPASSWORD` gives a password, is not looked at (not asked for in SEC-025; the driver calls that path deprecated); and the check is a model of what `pg` 8.23.1 and `pg-connection-string` 2.14.1 do with a connection string, so it must be compared with the driver again when either is updated (`tests/security/round7-recheck.test.ts` carries the model; the comparison itself needs the driver and is run by hand).
- The placeholder check refuses more than the driver would read as a placeholder, in the safe direction: a placeholder anywhere in the text of `DATABASE_URL` (a database or host name included), a placeholder whose escapes the driver would leave alone because another escape in the string is broken, and a placeholder encoded twice in the `password` query parameter. No password that is not built from a published placeholder is refused by it (tested with 18 near misses).
- While the database is down, the public health endpoint writes at most one error-level line per 30 seconds, whatever the number of requests and whatever the reason (SEC-026, fixed), with up to 300 characters of the driver's message, which can name the database host, port, and user. Accepted with the single limit: a failure whose reason differs from the one last written is not written until the interval ends (it is counted, and the next line carries the reason that holds then), and of the request ids of the 503 answers only the first of each line's count is in the log. Observed and not security-relevant: failed checks that fall inside the interval and are followed by a recovery stay in the count, and their first request id stays the one the next failure line carries, however much later that line is written; and a failure whose error object has a `message` that is not a string would be neither counted nor written (by reading; no such error is known from the database layer).
- A label of a broken-off body is written when it has the form of a class name or of an error code (SEC-027, fixed). The form keeps out anything with a blank, an `@`, a colon, a slash, a quote, or a non-ASCII letter, and anything over 64 characters. It does not keep out a single token: a digits-only code can be a phone number written without separators, and a dotted one an IPv4 address or a host name. Accepted, because both properties are set by the runtime today; **condition:** when the multipart reader of T-041 passes a form parser's errors to `requestBodyAborted`, that parser's `name` and `code` values are reviewed first.
- Requests refused before the rate limit (steps 1 to 4 of SR-05 item 5) use no allowance, and most endpoints have no rate limit at all. The application therefore does not bound how many requests a client sends, only what each may cost: no body is read for a caller that will be refused, and a body is at most its limit. A flood of cheap requests is for the proxy or the host to stop, and nothing is planned there.
- A signed-in account can send bodies up to the limit to every mutation that has no rate limit (cart, addresses, product edits) as fast as it likes. The cost per request is bounded (SR-05); the number of requests is not.
- A cart line whose product is hidden still shows that product's current title to the customer who holds the line (`docs/API_CONTRACTS.md` section 5.4: "the title stays"; the section does not say whether the picture and the slug stay too). That customer therefore keeps seeing content an admin took down, and sees an edit the seller made afterwards before any admin approved it. Only customers who put the product in their cart while it was visible are reached. Noted for backend-api and the cart task; not a registered finding, because nothing is built.
- A restore of a database backup undoes everything decided since the backup: ended sessions are valid again and deactivations, suspensions, and takedowns are lifted. SR-07 "Restore" requires every session deleted and every restriction back in force before the application serves; when the replaced database cannot be read, the restrictions can be reconstructed only as far as the server logs reach, and the audit log entries since the backup are lost in any case.
- An unpaid order holds its stock until the payment timeout, and an account may keep creating such orders. Short-lived with the mock provider by design; with a real provider a bound on unpaid orders per account is needed ("Scheduled work: security minimums").
- The blind resend of a refused checkout is prevented by the client only until item 8.2-1 of the contract is ruled on (position above; no ruling yet).
- Log retention and access (SR-06) depend entirely on deployment configuration: the retention setting of whatever stores the logs and of their backups, which named people hold accounts there, and whether the proxy's own access logs follow the same rule. None of it exists yet.
- 90 days is a maximum and the owner set no minimum (D-026, OQ-48). A host that keeps logs only briefly, or loses them at each release, is within the rule, and an incident found later than its logs lasted cannot be investigated from them. How long logs are actually kept is a deployment choice that has not been made.
- The investigation exception (SR-06 item 8) is a manual procedure: someone has to notice before day 90 that lines are evidence, copy only those, and write the record. Nothing enforces "only the relevant lines" or the deletion when the investigation closes except that record. Who may open and close such a hold is not named.
- Session removal (SR-07) is not designed. The bound is one day after expiry (D-026, OQ-49), and the MVP has no scheduled jobs: until T-015 chooses a mechanism that runs daily without traffic, the bound has nothing behind it. A clean-up job that stops silently breaks it unnoticed.
- Database backups are kept 30 days (D-026, OQ-50) and keep the address and browser details of sessions that existed when the backup was taken, for up to 30 days after the session itself is gone. Restoring a backup brings removed session rows back, which is why a restore ends with deleting every session (SR-07 "Restore"). No backup exists yet, so neither the 30 days nor who can read a backup is implemented.
- Suspending a store ends no session (D-027). What stops a suspended seller is only the status check on each request (TM-26); a seller service that forgets the check, or reads the status from a cached copy, leaves a suspended store acting with a valid session. To be proven per service when the seller module exists.
- The sign-in address stays in the server log for up to 90 days after the session it belonged to is gone. This follows from the two owner decisions together and is intended (SR-07 item 6).
- The wall clock drives rate-limit windows; a backward clock step lengthens windows and delays sweeps (fails towards refusing).
- No multi-factor authentication, including for admins.
- No email verification or password recovery until an email provider exists.
- No web application firewall, bot protection, or fraud detection.
- CSP strictness is limited by what the framework's inline scripts require.
- Local-disk file storage has no malware scanning.
- No independent human penetration test is planned within this project.
- Real payment integration will introduce webhook verification, replay protection, and reconciliation risks that the mock does not exercise.
- No dedicated secret scanner is installed locally or in CI yet.
