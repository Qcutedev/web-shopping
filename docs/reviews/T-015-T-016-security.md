## Findings

### SEC-032 One address can keep any account, an admin's included, from signing in
Severity: Medium
Status: OPEN
Location: src/server/auth/routes.ts:214 (per-email allowance consumed for every attempt, before the password is checked); src/server/rate-limit.ts:150 (`sign-in-email`, 5 per minute)
Description: The `sign-in-email` bucket is keyed by the email alone and is used up by any attempt. An attacker who knows an email sends five wrong passwords a minute from one address, and the owner, from any other address and with the right password, gets 429 for as long as the attacker keeps going. Five requests a minute from one address are under that address's own limit, so this costs the attacker nothing and needs no distributed source. An admin email is a natural target. SECURITY.md residual risks already named this trade-off and asked the auth task to count only failures; the implementation follows SR-05 item 5 instead, which counts every attempt. Counting only failures would not remove the lock-out either, because the attacker's attempts are failures. Availability only: no data or account is gained. Medium because it is cheap, targeted, and reaches admin accounts, not because of its impact on confidentiality.
Reproduction: `pnpm test:integration`, file `tests/security/t015-t016-auth.itest.ts`, the `it.fails` case "after five wrong passwords from one address, the owner signs in from another address" (with `it` it fails: `expected 429 to be 200`). The plain case beside it pins the current behaviour for an `ADMIN` account (429, no session row created).
Remediation: needs a decision by auth and the security owner. Recommended: key the strict per-email limit by email and client address together (`sign-in-email` subject `<address>|<email>`, 5 per minute), and add a looser per-email limit over all addresses (for example 30 per hour) that bounds distributed guessing. One address then cannot lock out an account; locking it requires many addresses for a long time. A rule change is a change of SR-02's capacity split. Alternatively, accept it with a written reason in SECURITY.md and remove the residual-risk sentence that promises otherwise. The fix is complete when the `it.fails` case turns red and is changed to `it`.
Re-check evidence: none yet.

### SEC-033 Sign-up display name accepts bidirectional control characters
Severity: Low
Status: OPEN
Location: src/modules/auth/schema.ts:21 and 26 (`NO_CONTROL_CHARACTERS` covers C0 and C1 only); src/modules/auth/bootstrap-admin.ts:136 (same schema for the admin name)
Description: The name is shown to other parties later (a buyer's name on a seller's order, a user list for admins). U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F, and U+061C are accepted, so a name can be displayed with its characters in another order than they are stored, for impersonation in admin and seller screens and in exported text. React escaping does not help: these are text, not markup.
Reproduction: `pnpm test:integration`, file `tests/security/t015-t016-auth.itest.ts`, six `it.fails` cases "a name with U+... is 400 VALIDATION_ERROR and creates nothing" (with `it` each fails: `expected 200 to be 400`). The plain case beside them shows that C0 and C1 controls are already refused.
Remediation: add the bidirectional formatting characters (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) to the refused set of the name schema, and use the same rule for every later free-text name field (store name, address name). Keep U+200B and U+200C allowed: Thai text uses them. As a second layer, the frontend renders user-supplied names inside `<bdi>` or with `unicode-bidi: isolate`.
Re-check evidence: none yet.

### SEC-034 The production session cookie uses the `__Secure-` prefix, not `__Host-`
Severity: Low
Status: OPEN
Location: src/server/auth/auth.ts:127-130 (`advanced.useSecureCookies` only); src/server/auth/cookies.ts:13-19 (the names the proxy and `readSession` look for)
Description: `__Secure-` requires the `Secure` flag but still allows a `Domain` attribute, so a page on a sibling or parent subdomain (for example a marketing site or a preview deployment under the same registrable domain) can set `__Secure-better-auth.session_token` for the shop's host. With an attacker's own valid session token, that signs the victim into the attacker's account (login CSRF), and whatever the victim then saves (an address, a seller application) lands in the attacker's account. `__Host-` forbids `Domain` and requires `Path=/`, which the cookie already meets. Deployment-dependent: harmless if no other host under the same registrable domain is ever controlled by someone else.
Reproduction: `pnpm test:integration`, file `tests/security/t015-t016-auth.itest.ts`, the `it.fails` case "the production session cookie carries the __Host- prefix" (with `it` it fails: `expected false to be true`).
Remediation: in production name the session cookie `__Host-better-auth.session_token`, with `Secure`, `Path=/`, and no `Domain`. better-auth 1.7.7 puts `__Secure-` in front of any name when `useSecureCookies` is true (`dist/cookies/index.mjs:23-32`), so this needs `useSecureCookies: false` together with `advanced.cookies.session_token = { name: "__Host-better-auth.session_token", attributes: { secure: true } }` in production. Check that no other cookie of the library is then written without `Secure`. Update `SESSION_COOKIE_NAMES` in `cookies.ts` and the production-mode cookie test. Alternatively record in DEPLOYMENT.md that no other host under the registrable domain may be operated by anyone else, and accept.
Re-check evidence: none yet.

### SEC-035 Response time tells a registered email from an unknown one
Severity: Low
Status: OPEN
Location: better-auth 1.7.7 `dist/api/routes/sign-in.mjs:318-337` (unknown email: `password.hash`; known email: `password.verify`) called from src/server/auth/routes.ts:219; `dist/api/routes/sign-up.mjs:192-240` (duplicate: one hash; new: one hash, a user insert, and an account insert) called from src/server/auth/routes.ts:171
Description: The bodies are identical (TM-03), but the time is not. Measured on loopback against the test database, 60 interleaved sign-ins each: unknown email median 60.1 ms, wrong password for a registered email median 61.9 ms; the two sorted series overlap only in their tails. Sign-up, 30 each: new email median 66.9 ms, duplicate 63.8 ms. Over the internet the jitter is larger and the per-email limit allows 5 samples a minute per email, so the attack is slow; for sign-up the functional enumeration already documented (sign up, then sign in with the chosen password) is cheaper. Recorded because TM-03 says the answers are identical, and the sign-in channel needs no account to be created.
Reproduction: steps, not a suite test (a timing test would be flaky in CI). Create a file `tests/security/zz-timing.itest.ts` that registers one email through `makeRuntime().auth.api.signUpEmail`, then 60 times alternately calls `handleSignIn` with a fresh runtime (own limiter, same `auth`) for a new random email and for the registered email, both with a wrong password, timing each call with `performance.now()`; run it with `pnpm exec vitest run --config vitest.integration.config.mts tests/security/zz-timing.itest.ts`; compare the medians; delete the file. Run on 2026-10-13 with the numbers above; the scratch file was deleted.
Remediation: give every failed sign-in, and every sign-up answer, the same minimum response time (for example: measure from the start of the password step and wait until a fixed floor such as 250 ms, plus a few milliseconds of random delay), in `routes.ts`, after the rate-limit checks so a refusal stays cheap. Re-measure with the steps above.
Re-check evidence: none yet.

### SEC-036 The production dependency tree holds `mysql2` with two published advisories
Severity: Low
Status: OPEN
Location: package.json (`better-auth` 1.7.7, which declares `mysql2 ^3.0.0` as an optional peer; pnpm installed `mysql2@3.15.3`)
Description: `pnpm audit --prod` was clean on 2026-10-12. Since better-auth was added it reports GHSA-rgwj-5xj2-c3m3 (high, plaintext credentials through an auth-plugin downgrade, fixed in 3.22.0) and a moderate decompression-bomb advisory (fixed in 3.23.1), path `.>better-auth>mysql2`. Not reachable: the application uses PostgreSQL, and in better-auth's `dist` only `test-utils/test-instance.mjs` imports `mysql2`. Low: hygiene, and a noisy audit hides a real advisory later.
Reproduction: `pnpm audit --prod` (exit 1, "2 vulnerabilities found, Severity: 1 moderate | 1 high"); `pnpm why mysql2 --prod`.
Remediation: devops: stop installing the unused optional peer (for example `auto-install-peers=false` for it, or a `pnpm.peerDependencyRules.ignoreMissing` entry for `mysql2`), or override it to `>=3.23.1`; then `pnpm audit --prod` must be clean. Record the choice in DECISIONS.md.
Re-check evidence: none yet.

## Observations that are not findings

- The `Origin` check, the content-type check, the rate limits, and the body limit are called in each auth handler by hand. Nothing enforces that a future mutation route does the same (already a residual risk in SECURITY.md, TM-16).
- `src/proxy.ts` builds the sign-in redirect from `request.nextUrl.origin`. If a shared cache in front of the application cached redirects without keying on `Host`, a forged `Host` could poison it. No cache exists; noted for the deployment task.
- `handleSignOut` answers 401 for a deactivated user's surviving session and does not clear the cookie. The session is useless anyway (`loadActor` returns null); cosmetic.
- Sessions are 7 days with no idle timeout and no re-authentication for admin actions. Not required by REQUIREMENTS; listed under residual risks.
- `security("info")` for the hourly purge line: confirmed as an acceptable use (one line an hour, counts only, a line SR-07 needs).
- The integration run writes the security events of the route modules to standard output. Harmless; test noise only.
