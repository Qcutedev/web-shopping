# T-041 upload module and file serving security review

Reviewer: security agent. Date: 2026-10-19. Commits reviewed: `d2298d1` (module), `c719f83` (routes, integration tests, contract 5.8.1). Also read: devops `c817572` (`UPLOAD_DIR` in `src/server/env.ts`). Tree at review: `c817572`; tests committed in `ba51042` (env fixtures) and `a250e5e` (T-041 tests).

Result: **no Critical or High finding.** Two new findings: SEC-065 (Medium, unattached uploads kept and served without end, no quota) and SEC-064 (Low, Exif GPS and all other metadata served byte for byte). CR-T040-07 answered: the 500 handler does not log Prisma `meta`. Register: [../SECURITY.md](../SECURITY.md).

A clean scanner run shows only that the scanner found nothing, and passing tests show only that the tested attacks fail. Neither shows that the upload endpoints are secure.

## What was checked and how

| Area | Result | Evidence |
| --- | --- | --- |
| Path traversal and key handling (TM-18) | Holds. Keys are `randomBytes(16)` as 32 lower-case hex, generated by the server. `isStorageKey` is checked first in `openFile` (no lookup, no file access for anything else); `LocalDiskStorage` re-checks every key (TypeError) and that the joined path stays under the resolved root. 20 hostile keys (traversal, both separators, drive letter, NUL, LF, trailing dot-extension, 31/33 digits, upper case, full-width and Arabic-Indic digits) are refused by both and nothing is created anywhere. A relative root is refused. Writes are exclusive (`wx`); a second write of one key fails with `EEXIST` and leaves the first bytes. | `t041-uploads.test.ts` "storage keys and the local disk adapter"; author's itest "is 404, identically, for ... traversal keys" |
| Client file name | Never used as a name or path, never stored, logged, or echoed. Separators, `:`, names starting with `..`, controls (C0, DEL, C1), percent-encoded separators and dots, and names over 255 are 400; no refusal repeats a byte of the name. Bidi controls in a name are accepted, which is harmless while the name is never shown. | "refuses client names that could be a path"; "never repeats any byte" |
| MIME, extension, magic bytes (TM-17) | Holds. Leading bytes decide the type (JPEG `FF D8 FF` + 1 byte; PNG signature + `IHDR`; WebP `RIFF`/`WEBP`/VP8 chunk with a fitting size); the declared part type and the extension must name the same type. SVG (also with a BOM), XML, HTML, GIF, PDF, empty, three JPEG bytes, a PNG signature without `IHDR`, and a non-WebP RIFF are 415 under every image name and type; `image/jpg`, `application/octet-stream`, a missing type, `a.jpg.html`, and a name without extension are 415. | "content checked by leading bytes"; "declared type and extension" |
| Size limits and streaming (SR-05) | Holds. A `Content-Length` over 5,259,264 or not plain decimal is 413 with nothing pulled; a body without a length is counted while read and stops at most one chunk past the limit; a file of 5,242,881 bytes inside a body under the limit is 413; exactly 5 MB is accepted; a body that breaks off is a 4xx. The reader is the JSON reader's `readBytesUpTo`, so the SEC-020 and SEC-021 controls apply. | "size and streaming" |
| Multipart framing | Holds; the parser is strict where readers usually differ. Refused with 400: `Content-Transfer-Encoding`, any header but the two, repeated headers, repeated parameters, `filename*`, folded headers, `attachment`, `form-dataX`, a preamble, bare-LF framing, header bytes that are not UTF-8, a part header over 8 KiB, an unclosed part, two files, an extra field before or after the file (`storeId`), `File` in another case, a file part without `filename`, no part, an empty body, a body framed with another boundary; boundary parameter missing, empty, repeated, over 70 characters, or holding `;`. Bytes after the closing delimiter are ignored and never parsed as a second file. A file whose bytes hold `CRLF--boundary` followed by anything but `--` or CRLF is refused, not truncated and accepted. The largest body full of near-delimiters parses in well under 2 s. | "refuses framing that another reader could read differently"; "carries the delimiter"; "parsing the largest body is cheap" |
| Polyglot images | Accepted by design, as documented in the contract: JPEG or PNG leading bytes followed by HTML and script are stored. Through the real routes such a file is served with the row's image type, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: no-store`, `Content-Disposition: inline`, no `Set-Cookie`, no CORS header, bytes unchanged; the type served does not follow the request's query, `Accept`, or `Content-Type`. | `t041-uploads.itest.ts` "a polyglot is served only as the image it claims to be"; unit "polyglot images" |
| Serving headers | As above; asserted on the response and pinned in the route source. Site-wide headers (HSTS, frame-ancestors on pages) remain TM-23 work. | itest polyglot case; "the file route is GET only ..." |
| Authorization, ownership, suspended store | Holds. The route checks origin, content type, session, `requireApprovedSeller`, then the `uploads` limit on `actor.userId`, then reads; the route file never names `storeId`. The service calls `requireApprovedStoreForWrite` first (share lock on the caller's own approved store), stores, then inserts by `INSERT ... SELECT ... WHERE s.id = storeId AND s.ownerId = userId AND s.status = 'APPROVED'`; zero rows is 403 and the bytes are deleted. The Store row is not written after the lock. A forged actor naming another seller's store, and a store suspended after step 4, store nothing (author's cases, run). A suspended store is refused before the body is read and its existing pictures stay public (by design). | Static route-order case; author's itest "createUpload: the store status is judged again"; reviewer's itest "what a suspension does" |
| Orphan bytes | A refused insert or a failed commit deletes the stored bytes; a failed delete leaves a file without a row that is never served, with one warn line naming the key. A partial write is unlinked by the adapter. But an upload that is stored and simply never attached is kept and served for ever: SEC-065. | Code read; author's unit cases in `service.test.ts`; reviewer's itest SEC-065 |
| Error logging | Upload refusals are ordinary 4xx without a cause and are not logged. Disk faults (`ENOSPC`, `EACCES`) become a 500 whose log line holds class and code only, so the file path in Node's message is not logged and nothing reaches the client. The warn lines carry the storage key only, which is a public identifier. | Code read of `errorResponse` and `describeErrorForLog`; CR-T040-07 cases |

## Findings

### SEC-065 An upload that nothing references is kept on disk and served for ever, with no quota (Medium, OPEN)

Full entry in [../SECURITY.md](../SECURITY.md). One approved seller can store about 3.5 GB a day of never-attached pictures (30 x 5 MB an hour) and they stay public at the marketplace's origin with no moderation and no removal path. The contract's cleanup job does not exist. Reproduction: `tests/security/t041-uploads.itest.ts` describe "SEC-065" (documented case and one `it.fails`, which flipped fails with `expected 200 to be 404`). Remediation: cleanup job, 404 for orphans past the grace period, per-store cap, admin takedown, separate volume with a disk alert.

### SEC-064 Uploaded images are stored and served byte for byte, camera location (Exif GPS) included (Low, OPEN)

Full entry in [../SECURITY.md](../SECURITY.md). Owner decides: re-encode (new dependency, also removes polyglots and caps dimensions), strip metadata segments, or accept and tell sellers. Reproduction: describe "SEC-064" (documented case and one `it.fails`, which flipped fails with `not to contain 'GPSLatitude'`).

### Observations (not findings)

1. **File route evaluates the storage before the key check.** `getUploadStorage()` is an argument of `openFile`, so with `UPLOAD_DIR` missing every `GET /api/files/...` (any key, anonymous) is a 500 with an error-level line. Since `c817572` production refuses to start without it, so this is a development and test matter only.
2. **A filesystem root as `UPLOAD_DIR`** (`/`, `C:\`) makes `root + sep` a doubled separator, so every key fails the inside-root check: uploads fail closed with a 500. Harmless; a sentence in DEPLOYMENT.md would save an operator the puzzle.
3. **`config.ts` and `env.ts` now both read `UPLOAD_DIR`.** `env.ts` also refuses NUL; `config.ts` does not (Node's fs refuses such a path anyway). The interim reader should go as `config.ts` itself says.
4. **Commit ambiguity.** If a commit succeeds but its acknowledgement is lost, the service deletes the bytes of a row that exists; the file then answers 404 with a warn line. Rare and fails closed.
5. **Polyglots and the shared origin.** The controls are the serving headers. Old browsers that ignore `nosniff`, and any future change that drops the sandbox CSP, are the risk; serving user files from a separate origin in production would remove the class (deployment option).
6. **Body held in full.** Up to 5,259,264 bytes per request before parsing; 30 concurrent requests of one approved seller hold about 158 MB. A stalled body is bounded by Node's `requestTimeout` only.
7. **`ARCHITECTURE.md` says `files/[...key]/`;** the single segment `[key]` that was built is the safer shape (orchestrator to update the document).
